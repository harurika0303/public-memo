# ADR-0003: タスク管理 API に集計・統計機能を含める

## ステータス
承認済み

## 背景

ポートフォリオプロジェクトとして「タスク管理 API」を実装するにあたり、機能範囲を決定する必要があった。

採用担当への訴求という観点では「CRUD + 認証だけで十分」という考え方と、「集計・統計機能まで含めることでデータ設計・SQL の能力も示せる」という考え方が対立した。

また、自分自身でも使いたいという動機があるため、実用性の観点からも機能選定を行った。

## 決定

**CRUD・JWT 認証に加えて、集計・統計エンドポイント（`/stats/*`）を含める。**

具体的には：
- `GET /stats/summary` — 全体の完了率・タスク件数
- `GET /stats/by-category` — カテゴリ別タスク数・完了率
- `GET /stats/overdue` — 期限切れタスク一覧

## 代替案

**案 A：CRUD + 認証のみ（採用せず）**

最もシンプルな構成。実装コストが最低で完成が早い。

- 不採用の理由：3エンティティ（ユーザー・カテゴリ・タスク）を使うなら集計は自然な拡張。集計がないと「なぜカテゴリを分けたのか」という設計意図が弱くなる。また自分が使いたいと思えるアプリにならない

**案 B：通知・リマインダー機能も含める（採用せず）**

期限前にメール通知するなど、より実用的な機能。

- 不採用の理由：バックグラウンドジョブ・メール送信インフラが必要になり、3言語での実装コストが大幅に上がる。ポートフォリオの完成を妨げるリスクが高い

## 結果

- 集計エンドポイントにより GROUP BY・集計関数・複合クエリの実装が含まれ、SQL / ORM の応用能力を示せる
- 3言語での実装で「同じ集計ロジックをどう書くか」の差分が明確になり、言語比較の観点でも価値が出る
- スコープが増えるため完成期間は若干延びるが、許容範囲内と判断した
