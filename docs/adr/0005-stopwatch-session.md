# ADR-0005: 学習記録アプリにストップウォッチ機能（進行中セッション）を追加する

## ステータス
承認済み

## 背景

学習記録アプリでは「今日何時間勉強したか」を記録するため、学習時間の入力方式を決定する必要があった。

最もシンプルな設計は「終わった後に何分勉強したかを数値で入力する」手動入力のみとすることだった。しかし要件定義の中で「ストップウォッチで入力したい」という要望が挙がり、2方式の併用を採用することになった。

ストップウォッチ機能を追加すると、StudySession エンティティに「進行中（IN_PROGRESS）」という状態が生まれ、状態管理のロジックが必要になる。

## 決定

**手動入力とストップウォッチの2方式を併用する。**

ストップウォッチは以下の2エンドポイントで実現する：
- `POST /sessions/start` — 進行中セッションを生成する
- `PATCH /sessions/:id/stop` — `ended_at` を記録し `duration_minutes` を自動計算して保存する

進行中セッションの制約：ユーザーごとに同時に1つまで。進行中セッションが存在する状態で `/sessions/start` を呼ぶと 409 を返す。

StudySession の `ended_at` が null である状態が「進行中」を意味する。

## 代替案

**案 A：手動入力のみ（採用せず）**

`duration_minutes` を直接入力する方式のみ。

- 不採用の理由：実際に自分が使いたいアプリとして、勉強を始めるときに「開始ボタン」を押して終わったら「終了ボタン」を押すというUXが自然。手動入力のみでは使いづらく、自分で使い続けるモチベーションが下がる

**案 B：POST /sessions に started_at のみ送って進行中を表現する（採用せず）**

start/stop を別エンドポイントに分けず、POST /sessions で `started_at` のみ・`ended_at` なしで送ることで進行中を表現する。

- 不採用の理由：手動入力（完了セッションの一括登録）とストップウォッチ（進行中セッションの作成）が同じエンドポイントになると、リクエストボディの解釈が複雑になる。エンドポイントを分けることで意図が明確になる

## 結果

- StudySession エンティティに `ended_at`（nullable）と `duration_minutes`（nullable）が必要になる
- 進行中セッションの存在チェックロジックが Session サービスに必要になる（409 制御）
- `GET /sessions/active` エンドポイントで現在の進行中セッションを取得できる
- 手動入力とストップウォッチが共存するため、どちらで作成されたセッションかは `duration_minutes` が最初から設定されているかどうかで区別できる
