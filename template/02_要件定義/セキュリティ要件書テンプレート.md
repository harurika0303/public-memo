# セキュリティ要件書

> **目的：** システムに求めるセキュリティ上の要件を定義する。設計・実装・テストの基準とし、脆弱性を作り込まないための共通認識を関係者間で持つ。
> **参照基準：** OWASP Top 10 / IPA「安全なウェブサイトの作り方」/ 社内セキュリティポリシー

## 1. 認証・認可

### 1.1 認証

| 項目                   | 要件                                                                            |
| ---------------------- | ------------------------------------------------------------------------------- |
| 認証方式               | メールアドレス + パスワード / OAuth2.0（Google等）/ SAML（SSO）                 |
| パスワードポリシー     | 〇〇文字以上、大文字・小文字・数字・記号を含む                                  |
| パスワードの保存       | bcrypt / Argon2id 等の強ハッシュ関数でハッシュ化して保存。平文・MD5・SHA1は禁止 |
| ブルートフォース対策   | 〇〇回連続失敗でアカウントロック（〇〇分）                                      |
| 多要素認証（MFA）      | 必須 / 任意 / 対応しない                                                        |
| セッション有効期限     | ログイン後〇〇時間。無操作〇〇分でセッション切れ                                |
| セッション固定攻撃対策 | ログイン成功時にセッションIDを再生成する                                        |

### 1.2 認可

| 項目             | 要件                                                                                |
| ---------------- | ----------------------------------------------------------------------------------- |
| アクセス制御方式 | RBAC（ロールベース）/ ABAC                                                          |
| ロール定義       | 別途権限マトリクスで定義する（画面定義書参照）                                      |
| 水平アクセス制御 | 他ユーザーのデータにアクセスできないこと（URLの直打ち・IDの推測で取得できないこと） |
| 管理者機能       | 管理者権限のある操作はロールチェックを必ず行う                                      |

## 2. 通信・データ保護

| 項目                | 要件                                                                           |
| ------------------- | ------------------------------------------------------------------------------ |
| 通信の暗号化        | 全ての通信をHTTPS（TLS 1.2以上）で行う。HTTP接続はHTTPSへリダイレクト          |
| HSTS                | `Strict-Transport-Security` ヘッダーを設定する                                 |
| 証明書              | 有効なSSL証明書を使用する。自己署名証明書は本番では使用しない                  |
| 機密データの保存    | 個人情報・決済情報は暗号化して保存する（AES-256等）                            |
| APIキー・パスワード | ソースコードにハードコードしない。環境変数・シークレットマネージャーで管理する |

---

## 3. 入力値検証・出力エスケープ

| 項目                         | 要件                                                                                                  |
| ---------------------------- | ----------------------------------------------------------------------------------------------------- |
| SQLインジェクション対策      | プレースホルダー（バインドパラメーター）を使用する。動的SQLでの文字列連結は禁止                       |
| XSS対策                      | テンプレートエンジンの自動エスケープを使用する。`innerHTML` への直接代入は禁止                        |
| CSRF対策                     | 状態を変更するリクエスト（POST/PUT/DELETE）にはCSRFトークンを使用する                                 |
| コマンドインジェクション対策 | ユーザー入力をシェルコマンドに渡さない                                                                |
| ファイルアップロード         | 拡張子・MIMEタイプを検証する。アップロードされたファイルをWebサーバーの公開ディレクトリに直接置かない |
| リダイレクト                 | オープンリダイレクトを防ぐため、リダイレクト先URLをホワイトリストで制限する                           |

## 4. セキュリティヘッダー

| ヘッダー                  | 設定値                            | 目的                      |
| ------------------------- | --------------------------------- | ------------------------- |
| `Content-Security-Policy` | `default-src 'self'; ...`         | XSS・インジェクション防止 |
| `X-Frame-Options`         | `DENY` または `SAMEORIGIN`        | クリックジャッキング防止  |
| `X-Content-Type-Options`  | `nosniff`                         | MIMEスニッフィング防止    |
| `Referrer-Policy`         | `strict-origin-when-cross-origin` | リファラー漏洩防止        |
| `Permissions-Policy`      | 必要なAPIのみ許可                 | ブラウザAPI制限           |

---

## 5. ログ・監査

| 項目                 | 要件                                                                   |
| -------------------- | ---------------------------------------------------------------------- |
| 認証ログ             | ログイン成功・失敗・ログアウトを記録する                               |
| 操作ログ             | データの作成・更新・削除操作を記録する（操作者・日時・対象データのID） |
| ログの保持期間       | 〇〇ヶ月間保持する                                                     |
| ログへの個人情報含有 | パスワード・カード番号等の機密情報をログに出力しない                   |
| ログの改ざん防止     | ログファイルへの書き込み権限を実行ユーザーのみに制限する               |
| 不正アクセス検知     | 短時間での大量リクエスト・ブルートフォースをアラート通知する           |

---

## 6. 個人情報・データ保護

| 項目           | 要件                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| 個人情報の定義 | 〇〇（氏名・メールアドレス・〇〇）を個人情報として扱う                     |
| 最小権限の原則 | 業務上必要な担当者のみが個人情報にアクセスできること                       |
| データの削除   | 退会・契約終了後〇〇ヶ月で個人情報を削除または匿名化する                   |
| テストデータ   | 本番の個人情報をテスト環境に使用しない。マスキング・ダミーデータを使用する |

---

## 7. 第三者コンポーネント管理

| 項目                     | 要件                                                                  |
| ------------------------ | --------------------------------------------------------------------- |
| OSS・ライブラリの管理    | `composer.lock` / `package-lock.json` でバージョンを固定して管理する  |
| 脆弱性スキャン           | リリース前にSCA（ソフトウェア構成分析）ツールで既知の脆弱性を確認する |
| セキュリティアップデート | 重大な脆弱性が発見されたライブラリは〇〇営業日以内に更新する          |

---

## 8. セキュリティテスト要件

| テスト種別                         | タイミング                    | 実施者                 | 合格基準                           |
| ---------------------------------- | ----------------------------- | ---------------------- | ---------------------------------- |
| コードレビュー（セキュリティ観点） | 実装完了後                    | 開発チーム             | 指摘事項がすべて対応済みであること |
| 脆弱性診断（自動スキャン）         | システムテスト前              | 開発チーム（ツール）   | CriticalおよびHighが0件            |
| ペネトレーションテスト             | リリース前（初回のみ / 毎回） | 外部セキュリティ専門家 | 高リスク以上の指摘が0件            |

## 9. インシデント対応

| 項目                 | 要件                                                           |
| -------------------- | -------------------------------------------------------------- |
| 情報漏洩発生時の報告 | 発覚後〇時間以内に経営層・情報セキュリティ担当に報告する       |
| 影響ユーザーへの通知 | 個人情報が漏洩した場合、〇〇日以内に対象ユーザーに通知する     |
| 証拠保全             | インシデント発生時はログ・スナップショットを削除・上書きしない |
