## 6. テスト合格基準

### 各レベルの合格基準

| テストレベル   | 合格条件                                                                      |
| -------------- | ----------------------------------------------------------------------------- |
| 単体テスト     | 全テスト項目がPASS（カバレッジ〇〇%以上を目標）                               |
| 結合テスト     | 全テストケースがPASS、または重要度「軽微」以外のバグが未解決でないこと        |
| システムテスト | 全テストケースの〇〇%以上がPASS、かつ「致命的」「重要」バグが未解決でないこと |
| UAT            | ユーザー代表が合格と判断し、署名による承認を得ること                          |

### バグ重要度の定義

| 重要度     | 定義                                       | リリースへの影響       |
| ---------- | ------------------------------------------ | ---------------------- |
| **致命的** | システムが使用不能になる、データが破損する | 修正なしにリリース不可 |
| **重要**   | 主要業務が遂行できない、回避手段がない     | 原則修正してリリース   |
| **軽微**   | 軽微な表示崩れ、回避手段がある             | リリース後対応可       |

## 7. テスト方針・アプローチ

| 項目                     | 方針                                                                |
| ------------------------ | ------------------------------------------------------------------- |
| **テスト設計技法**       | 同値分割・境界値分析・デシジョンテーブルを中心に使用する            |
| **自動化方針**           | 単体テスト：自動化必須 / システムテスト：主要〇〇シナリオのみ自動化 |
| **リグレッションテスト** | バグ修正のたびに、修正箇所と関連機能を再テストする                  |
| **探索的テスト**         | システムテスト終盤に〇〇時間を確保して実施する                      |
| **セキュリティテスト**   | OWASP Top 10 を基準にチェック（SQL注入・XSS等）                     |
| **性能テスト**           | 同時接続〇〇人の条件で主要API・画面のレスポンスタイムを計測する     |
