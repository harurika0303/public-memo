# コーディング規約

> **目的：** チームメンバー全員が同じスタイルでコードを書き、可読性・保守性・レビュー効率を高める。
> **適用範囲：** 本プロジェクトの全ソースコードに適用する。既存コードの一括修正は不要だが、新規作成・修正時には必ず本規約に従う。
> **更新ルール：** 規約を変更する場合はチームで合意を取り、本文書を更新してからコードに反映する。

## 1. 命名規則

### 1.1 共通ルール

| 対象                 | 形式                         | 例                                      |
| -------------------- | ---------------------------- | --------------------------------------- |
| クラス名             | PascalCase                   | `UserService`, `OrderController`        |
| メソッド・関数名     | camelCase                    | `getUserById()`, `calculateTotal()`     |
| 変数名               | camelCase                    | `userName`, `totalPrice`                |
| 定数                 | UPPER_SNAKE_CASE             | `MAX_RETRY_COUNT`, `DEFAULT_ROLE`       |
| ファイル名（クラス） | PascalCase（クラス名と一致） | `UserService.php`, `UserService.ts`     |
| ファイル名（その他） | kebab-case                   | `user-list.vue`, `api-client.ts`        |
| DBテーブル名         | snake_case・複数形           | `users`, `order_items`                  |
| DBカラム名           | snake_case                   | `created_at`, `user_id`                 |
| APIエンドポイント    | kebab-case・複数形           | `/api/users`, `/api/order-items`        |
| ブランチ名           | kebab-case                   | `feature/user-login`, `fix/login-error` |

### 1.2 名前付けの方針

- **省略しない：** `usr` より `user`、`btn` より `button` を使う（ID・略語として広く定着しているものを除く）
- **意味が分かる名前にする：** `data`・`tmp`・`temp`・`flag` などの汎用名は避ける
- **否定形の boolean は避ける：** `isNotValid` より `isInvalid`、`disabled` より `isDisabled`
- **動詞で始める（関数）：** `get〇〇`, `create〇〇`, `update〇〇`, `delete〇〇`, `is〇〇`, `has〇〇`, `can〇〇`

## 2. コードフォーマット

| 項目           | ルール                                                                     |
| -------------- | -------------------------------------------------------------------------- |
| インデント     | スペース4つ（タブ不可）                                                    |
| 行末の空白     | 禁止                                                                       |
| 最大行長       | 120文字（超える場合は改行する）                                            |
| 文末セミコロン | 言語の慣例に従う（TypeScript: あり / Python: なし）                        |
| 引用符         | シングルクォートを優先（テンプレートリテラルが必要な場合はバッククォート） |

**自動フォーマッター：** Prettier / PHP-CS-Fixer / Black 等（プロジェクトに合わせて設定する）

## 3. コメント規則

| 種別                     | ルール                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| ファイルヘッダー         | 不要（Gitの履歴で管理する）                                                                 |
| クラスコメント           | 責務を1〜2文で説明する                                                                      |
| メソッドコメント         | 複雑なロジックを持つメソッドのみ記述する。単純なCRUDは不要                                  |
| インラインコメント       | 「なぜそうしているか（Why）」を書く。「何をしているか（What）」はコードから読める場合は不要 |
| TODO / FIXME             | `// TODO: 内容（担当者名）` の形式で記述する。リリース前に必ず解消する                      |
| 不要コメントアウトコード | コミットに含めない（Gitで管理する）                                                         |

## 4. ファイル・ディレクトリ構成

<!-- プロジェクトのフレームワーク・構成に合わせて記述する -->

```
src/
  controllers/    # リクエスト受付・レスポンス返却のみ
  services/       # ビジネスロジック
  repositories/   # DBアクセスのみ
  models/         # データ構造・バリデーション定義
  utils/          # 汎用ヘルパー関数
  types/          # 型定義（TypeScriptの場合）
tests/
  unit/           # 単体テスト（サービス層を中心に）
  integration/    # 結合テスト（APIエンドポイント）
```

## 5. テスト規則

| 項目             | ルール                                                        |
| ---------------- | ------------------------------------------------------------- |
| テストファイル名 | 対象ファイル名 + `.test.ts` / `Test.php`                      |
| テスト関数名     | 「〇〇のとき、〇〇になること」を日本語または英語で記述する    |
| カバレッジ目標   | サービス層：〇〇%以上                                         |
| モック方針       | 外部API・DBアクセスはモックに置き換える                       |
| テストデータ     | ファクトリ関数 / フィクスチャで管理する（ハードコードしない） |

## 6. セキュリティ規則

| ルール                     | 詳細                                                                       |
| -------------------------- | -------------------------------------------------------------------------- |
| 秘密情報のハードコード禁止 | APIキー・パスワード・接続文字列はソースコードに書かず、環境変数で管理する  |
| SQLインジェクション対策    | プリペアドステートメント / ORMを使い、文字列結合でSQLを作らない            |
| XSS対策                    | テンプレートエンジンのエスケープ機能を使い、`innerHTML` の直接操作を避ける |
| 認証チェック               | APIエンドポイントに認証ミドルウェアを適用し、チェック漏れを防ぐ            |
| ログに個人情報を含めない   | パスワード・メールアドレス等はマスキングしてログ出力する                   |
| 依存パッケージの脆弱性     | `npm audit` / `composer audit` 等を定期実行する                            |

## 7. Git・ブランチ運用ルール

### ブランチ戦略

| ブランチ       | 用途                     | マージ先             |
| -------------- | ------------------------ | -------------------- |
| `main`         | 本番リリース済みのコード | —                    |
| `develop`      | 開発中の統合ブランチ     | `main`（リリース時） |
| `feature/〇〇` | 機能開発                 | `develop`            |
| `fix/〇〇`     | バグ修正                 | `develop`            |
| `hotfix/〇〇`  | 本番緊急修正             | `main` + `develop`   |

### コミットメッセージ規則

```
<種別>: <変更内容の概要>（50文字以内）

[任意] 詳細説明（必要な場合のみ。何をしたかでなく、なぜそうしたかを書く）
```

| 種別       | 使い場面                                       |
| ---------- | ---------------------------------------------- |
| `feat`     | 新機能の追加                                   |
| `fix`      | バグ修正                                       |
| `refactor` | 動作を変えないリファクタリング                 |
| `docs`     | ドキュメントのみの変更                         |
| `test`     | テストの追加・修正                             |
| `chore`    | ビルド・設定ファイルの変更                     |
| `style`    | フォーマット・空白等の修正（動作に影響しない） |

**例：**
```
feat: ユーザーログイン機能を追加

JWTトークンを使ったステートレス認証を採用した。
セッション管理のスケールアウトを考慮した設計とするため。
```

### プルリクエスト（PR）ルール

| 項目           | ルール                                                   |
| -------------- | -------------------------------------------------------- |
| PRのサイズ     | 1PRで変更するファイルは〇〇以内を目安とする              |
| レビュアー数   | 最低1名のApprovalが必要                                  |
| セルフレビュー | PRを出す前に自分でdiffを確認する                         |
| CIの確認       | CI（自動テスト）がグリーンになってからレビューを依頼する |
| マージ方法     | Squash merge / Merge commit（プロジェクトで統一する）    |

## 8. コードレビューの観点

| 観点           | 確認内容                                       |
| -------------- | ---------------------------------------------- |
| 動作           | 仕様通りに動くか                               |
| セキュリティ   | 本規約のセキュリティルールを守っているか       |
| 命名           | 本規約の命名規則を守っているか                 |
| 可読性         | 変数名・関数名・コメントから意図が読み取れるか |
| テスト         | 重要なロジックにテストが書かれているか         |
| パフォーマンス | N+1問題・不要なループ等がないか                |
| 重複           | 既存のユーティリティ関数で代替できないか       |
