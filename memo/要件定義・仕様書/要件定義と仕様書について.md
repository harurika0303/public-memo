## 1. 要件定義とは

### 1.1 定義

**要件定義（Requirements Definition / Requirements Engineering）** とは、開発対象のシステムやソフトウェアに対して、ステークホルダーが求める条件・制約・期待を収集・分析・文書化するプロセスである。

> *"Requirements engineering focuses on the tasks that determine the needs or conditions to meet the new or altered product or project."*
> — IEEE/Wikipedia (Requirements Analysis)

要件定義は、ウォーターフォール開発においてはソフトウェア開発ライフサイクルの最初のフェーズとして位置づけられる。アジャイル開発においても、反復的に継続されるプロセスとして認識されている（ISO/IEC/IEEE 29148:2018）。

### 1.2 目的

- ステークホルダーとシステム開発者の間で「何を作るか」の合意基盤を形成する
- 後工程での手戻りコスト・リスクを低減する
- プロジェクトのコスト・リスク・スケジュールの見積もり根拠を提供する
- テスト・受入基準の基礎となる

---

## 2. 要件工学（Requirements Engineering）のプロセス

ISO/IEC/IEEE 29148:2018 および SWEBOK に基づく標準的なプロセスは以下の通り。

### 2.1 プロセスの流れ

```
① 要件引き出し（Elicitation）
        ↓
② 要件分析・交渉（Analysis & Negotiation）
        ↓
③ システムモデリング（System Modeling）
        ↓
④ 要件仕様化（Specification）
        ↓
⑤ 要件検証（Validation）
        ↓
⑥ 要件管理（Management）
```

### 2.2 各フェーズの説明

| フェーズ                 | 内容                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| **① 要件引き出し**       | ステークホルダーへのインタビュー、ワークショップ、ユースケース作成、観察調査などにより要件を収集する |
| **② 要件分析・交渉**     | 収集した要件を整理・分析し、ステークホルダー間の矛盾・競合を解消する                                 |
| **③ システムモデリング** | UML等を用いてシステムの動作・構造を図式化する（ユースケース図、シーケンス図等）                      |
| **④ 要件仕様化**         | 要件を公式文書（要件定義書・仕様書）として記述・体系化する                                           |
| **⑤ 要件検証**           | 文書化された要件がステークホルダーのニーズを満たしているか確認する                                   |
| **⑥ 要件管理**           | 要件の変更・追跡・トレーサビリティを継続的に管理する                                                 |

## 3. 要件の種類

SWEBOK・ISO/IEC/IEEE 29148・経済産業省「非機能要求グレード」に基づく分類。

### 3.1 機能要件（Functional Requirements）

システムが**何をすべきか**を定義する要件。

- ユーザが実行できる操作・機能
- システムが処理すべきデータ
- システムの振る舞い・入出力

> *"Functional requirements explain what has to be done by identifying the necessary task, action or activity that must be accomplished."*
> — Wikipedia (Requirements Analysis)

**例：**
- ユーザは商品をカートに追加できる
- 管理者は月次レポートをCSV形式でエクスポートできる

### 3.2 非機能要件（Non-Functional Requirements）

システムが**どのように動作すべきか**を定義する品質特性の要件。

> *"Non-functional requirements specify criteria that can be used to judge the operation of a system, rather than specific behaviors."*
> — Wikipedia (Requirements Analysis)

経済産業省「非機能要求グレード」では以下の大分類を定義している：

| カテゴリ                     | 内容例                                     |
| ---------------------------- | ------------------------------------------ |
| **可用性**                   | 稼働率、計画停止時間、障害時の許容停止時間 |
| **性能・拡張性**             | 応答時間、スループット、データ量の拡張性   |
| **運用・保守性**             | 監視方法、バックアップ・リストア要件       |
| **移行性**                   | 既存システムからのデータ移行方法・期間     |
| **セキュリティ**             | 認証・認可、暗号化、不正アクセス対策       |
| **システム環境・エコロジー** | 設置環境、消費電力、法規制対応             |

### 3.3 その他の要件分類

| 分類                                     | 内容                                           |
| ---------------------------------------- | ---------------------------------------------- |
| **ビジネス要件**                         | 高レベルの業務目標・成果目標                   |
| **ユーザー要件（ステークホルダー要件）** | ユーザーがシステムを使って達成したいこと       |
| **システム要件**                         | ビジネス・ユーザー要件を実現するシステムの仕様 |
| **制約条件**                             | 法規制、予算、スケジュール、技術的制限など     |

## 4. 要件の品質基準

ISO/IEC/IEEE 29148:2018 では、個々の要件および要件集合に対して以下の品質基準を定めている。

### 4.1 個別要件の品質

| 品質特性                     | 説明                                         |
| ---------------------------- | -------------------------------------------- |
| **必要性（Necessary）**      | その要件がなければシステムは不完全である     |
| **適切性（Appropriate）**    | 詳細度・抽象度が適切である                   |
| **明確性（Unambiguous）**    | 一意に解釈可能である                         |
| **完全性（Complete）**       | 必要な情報が全て含まれている                 |
| **単独性（Singular）**       | 一つの要件に複数の内容を混在させない         |
| **実現可能性（Feasible）**   | 技術的・予算的に実現可能である               |
| **検証可能性（Verifiable）** | テストや検査で確認可能である                 |
| **正確性（Correct）**        | ステークホルダーのニーズを正確に表現している |
| **適合性（Conforming）**     | 組織のルール・標準に準拠している             |

### 4.2 要件集合の品質

| 品質特性                           | 説明                                           |
| ---------------------------------- | ---------------------------------------------- |
| **完全性（Complete）**             | 全てのステークホルダーニーズが網羅されている   |
| **一貫性（Consistent）**           | 要件間で矛盾・競合がない                       |
| **実現可能性（Feasible）**         | 制約条件の下で実現可能である                   |
| **理解可能性（Comprehensible）**   | ステークホルダーが理解できる形で記述されている |
| **適格性（Able to be validated）** | 要件が検証・妥当性確認できる                   |

### 4.3 避けるべき記述（Requirements Smells）

以下の表現は要件の品質を低下させる（Femmer et al., 2017）：

- 主観的言語（「使いやすい」「適切な」）
- 曖昧な副詞・形容詞（「迅速に」「十分な」）
- 最上級表現（「最大の」「最高の」）
- 否定表現（「〜しない」だけの記述）
- 検証不可能な表現（「常に」「全て」）

## 5. 成果物：要件定義書と仕様書

### 5.1 文書の位置づけ

```
ビジネス要件仕様書（BRS: Business Requirements Specification）
        ↓
ステークホルダー要件仕様書（StRS: Stakeholder Requirements Specification）
        ↓
システム要件仕様書 / ソフトウェア要件仕様書（SRS: Software Requirements Specification）
```

ISO/IEC/IEEE 29148:2018 はこの三層構造を定義している。実務では「要件定義書」がBRS＋StRS相当、「仕様書（基本設計書・機能仕様書）」がSRS相当に対応することが多い。

### 5.2 SRS（ソフトウェア要件仕様書）の標準構成

IEEE 830-1998 および ISO/IEC/IEEE 29148:2018 に基づく構成例：

```
1. 目的（Purpose）
   1.1 定義・用語集
   1.2 背景・経緯
   1.3 システム概要
   1.4 参照文書

2. 全体説明（Overall Description）
   2.1 製品の視点（既存システム・外部システムとの関係）
   2.2 製品の機能概要
   2.3 ユーザー特性
   2.4 制約・前提・依存関係

3. 個別要件（Specific Requirements）
   3.1 外部インターフェース要件
      - ユーザーインターフェース
      - ハードウェアインターフェース
      - ソフトウェアインターフェース
      - 通信インターフェース
   3.2 機能要件
   3.3 非機能要件
      - 性能要件
      - セキュリティ要件
      - 信頼性・可用性要件
      - 保守性要件
      - 移植性要件
   3.4 データベース要件
   3.5 設計制約
   3.6 ソフトウェアシステム属性

4. 検証アプローチ（Verification Approaches）

付録
   A. 用語集
   B. 分析モデル（ユースケース図、ER図等）
   C. 課題リスト
```

## 6. 要件引き出し技法

| 技法                       | 説明                                             | 適用場面             |
| -------------------------- | ------------------------------------------------ | -------------------- |
| **インタビュー**           | ステークホルダーへの個別ヒアリング               | 業務知識の深掘り     |
| **ワークショップ（JRD）**  | 複数ステークホルダーによる共同要件定義セッション | 部門横断的な要件整合 |
| **ユースケース分析**       | システムとアクターの相互作用をシナリオで記述     | 機能要件の整理       |
| **ユーザーストーリー**     | アジャイル開発で使用する簡易シナリオ形式         | アジャイル開発       |
| **プロトタイピング**       | モックアップ・試作品によるニーズ確認             | UI/UX要件の具体化    |
| **観察・エスノグラフィー** | 実際の業務現場を観察して暗黙知を引き出す         | 現場業務の実態把握   |
| **ドキュメント分析**       | 既存業務規程・帳票・システム仕様を分析           | 既存システムの移行   |

## 7. ステークホルダーの識別

要件定義においてステークホルダーを正しく識別することは不可欠である（SWEBOK・ISO/IEC/IEEE 29148）。

主なステークホルダーの例：

- **エンドユーザー**：システムを直接操作する担当者
- **業務責任者（スポンサー）**：システム導入の意思決定者・予算承認者
- **IT部門・システム管理者**：システムの運用・保守担当者
- **外部規制機関**：法規制・業界標準への適合を求める機関
- **外部連携システムの所有者**：APIや連携データを提供する組織
- **開発チーム**：要件を受け取り、実装する技術者

## 8. よくある失敗と対策

### 8.1 ユーザー側の問題（Steve McConnell, *Rapid Development* より）

- 何が欲しいか自分でも明確でない
- 書面での要件確定を嫌がる
- 開発開始後に要件を追加・変更する
- レビューに参加しない
- 開発プロセスを理解していない

### 8.2 開発者側の問題

- 要件定義が完了する前にコーディングを開始する
- ユーザーと開発者で用語・認識が異なる
- 既存システムや技術的都合に合わせて要件を解釈する

### 8.3 対策

- ビジネスアナリスト（BA）やシステムアナリストの活用
- プロトタイプによる早期ビジュアライゼーション
- UML・ユースケース図などを用いた共通言語の確立
- 要件のトレーサビリティマトリクスの作成・維持

## 9. 要件定義と仕様書の違い（実務上の整理）

| 項目                 | 要件定義書                           | 仕様書（機能仕様書・基本設計書）        |
| -------------------- | ------------------------------------ | --------------------------------------- |
| **問い**             | 「何を実現するか（What）」           | 「どのように実現するか（How）」         |
| **視点**             | ビジネス・ユーザー視点               | システム・技術視点                      |
| **作成者**           | BA・ユーザー代表・PM                 | SE・アーキテクト                        |
| **対応する国際標準** | BRS / StRS（ISO/IEC/IEEE 29148）     | SRS（ISO/IEC/IEEE 29148 / IEEE 830）    |
| **内容**             | 業務フロー、ユースケース、業務ルール | 画面設計、API仕様、DB設計、処理ロジック |
| **承認者**           | 発注者・業務責任者                   | 開発チームリード・アーキテクト          |

> **重要：** 要件定義書は「設計に依存しない（design-independent）」記述を原則とする。
> *"Requirements should strictly be about what is needed, independently of the system design."*
> — ISO/IEC/IEEE 29148:2018
