# AIに1からアプリを全自動で作らせる方法

> **作成日**: 2026年5月24日  
> **対象**: GitHub Copilot / Claude Code / Cursor などの AI エージェントツール全般

---

## 0. 全自動開発とは何か

AI エージェントは、単なる「コード補完ツール」ではなく、**ファイルの読み書き・コマンド実行・テスト・PR 作成まで自律的にこなせる作業者**として動作できる。

```
全自動開発の流れ (理想形):
  人間が仕様を書く
      ↓
  AI がコードベースを探索・設計
      ↓
  AI が実装
      ↓
  AI がテストを実行・修正
      ↓
  AI がコミット・PR を作成
      ↓
  人間がレビューするだけ
```

**ただし「指示が曖昧 → 期待外れの成果物」となりやすい**。  
全自動に近づけるには、AIへの指示を「仕様書」として事前に整備しておくことが鍵。

## 2. 全自動化のための「指示書ファイル」一覧

### 2-1. `CLAUDE.md`（Claude Code 専用）

プロジェクトルートに置くと、**セッション開始時に毎回自動で読み込まれる**。  
「この会話が始まるたびに伝えるべき情報」を書く。

```markdown
# プロジェクト概要
Laravel + Vue.js の在庫管理 SPA。

# ビルド・起動
- composer install && npm install
- php artisan migrate --seed
- npm run dev

# テスト実行
- php artisan test
- npm run test

# コードスタイル
- PHP: PSR-12 準拠
- JS: ESModules (import/export) を使う。CommonJS (require) は禁止
```

> **ポイント**: 長すぎると AI が後半を無視する。「これがなかったら AI が間違いを犯すか?」を基準に削ぎ落とす。

---

### 2-2. `.github/copilot-instructions.md`（GitHub Copilot 専用）

リポジトリ全体に適用される Copilot 向けの指示。  
GitHub 上の Copilot エージェント（cloud agent）にも読み込まれる。

```markdown
## 技術スタック
- バックエンド: Laravel 11 / PHP 8.3
- フロントエンド: Vue 3 + TypeScript + Vite
- DB: MySQL 8.0
- コンテナ: Docker Compose

## ディレクトリ構造
- app/Models/          : Eloquent モデル
- app/Http/Controllers/: コントローラ
- resources/js/        : Vue コンポーネント

## ルール
- マイグレーションは必ず down() も実装すること
- API レスポンスは { data, message, status } の形式に統一すること
```

---

### 2-3. `AGENTS.md`（複数ツール共通）

Cursor・GitHub Copilot・ChatGPT Codex など **複数ツールが読める汎用フォーマット**。  
プロジェクトルートかサブディレクトリに置く。ネストしたディレクトリのファイルが優先される。

```markdown
# プロジェクト指示書

## アーキテクチャ
- Repository パターンを使う
- ビジネスロジックは Service レイヤーに書く

## コード規約
- TypeScript を必ず使う
- React コンポーネントは関数型のみ
- DB カラム名はスネークケース
```

---

### 2-4. Cursor の `.cursor/rules/*.mdc`

より細粒度な制御が可能。ファイルの種類ごとにルールを分けられる。

```markdown
---
globs: src/components/**/*.tsx
alwaysApply: false
---
- named exports を使う（default export は禁止）
- コンポーネントは 200 行以内に収める
- スタイルはモジュール CSS ファイルをコンポーネントと同じディレクトリに置く
```

## 3. 全自動開発のための「ワークフロー」

### 3-1. 推奨フロー（4フェーズ）

```
Phase 1: 探索（Explore）
  AI に「変更なしで読み込みだけ」させる
  例: "read /src/auth を読んでセッション管理の仕組みを理解して"

Phase 2: 計画（Plan）
  AI に実装計画を立てさせる
  例: "Google OAuth を追加したい。変更が必要なファイルと実装手順を挙げて"

Phase 3: 実装（Implement）
  コードを書かせる + テスト実行
  例: "計画通りに実装して。テストも書いてスイートを実行して失敗を直して"

Phase 4: コミット（Commit）
  例: "わかりやすいメッセージでコミットして PR を作って"
```

---

### 3-2. インタビュー方式（大規模機能向け）

仕様が曖昧なまま実装させるより、**AI に質問させて仕様を固めてからコーディング**させる方が品質が上がる。

```
プロンプト例:
「[機能の概要] を作りたい。AskUserQuestion ツールを使って私にインタビューしてくれ。
技術実装・UI/UX・エッジケース・トレードオフについて掘り下げて質問すること。
全部聞き終わったら SPEC.md に完全な仕様書を書いてくれ。」
```

仕様が固まったら **新しいセッションを開始**して実装に集中させる。

## 4. 指示書に書くべき内容チェックリスト

### 【必須】プロジェクト基本情報
- [ ] アプリの目的・概要（1〜3行）
- [ ] 使用言語・フレームワーク・主要ライブラリとバージョン
- [ ] ディレクトリ構造の説明（主要フォルダの役割）

### 【必須】セットアップ・ビルド手順
- [ ] 依存関係インストールコマンド
- [ ] ビルドコマンド
- [ ] 開発サーバー起動コマンド
- [ ] **テスト実行コマンド**（最重要）
- [ ] Lint / 型チェックコマンド

### 【推奨】コード規約
- [ ] ファイル命名規則
- [ ] 命名規則（変数・関数・クラス）
- [ ] 禁止パターン（「CommonJS 禁止」「any 禁止」など）
- [ ] アーキテクチャパターン（MVC / Repository / Service など）

### 【推奨】プロジェクト固有のルール
- [ ] API レスポンス形式
- [ ] エラーハンドリング方針
- [ ] 認証・認可の仕組みの説明
- [ ] DB マイグレーション方針

### 【任意】CI/CD 情報
- [ ] GitHub Actions 等のワークフロー概要
- [ ] プルリクエストのルール
- [ ] ブランチ命名規則

## 5. 効果的なプロンプトの書き方

### 5-1. タスクを具体的に定義する

| 悪い例                     | 良い例                                                                                                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `テストを書いて`           | `foo.py のテストを書いてくれ。ユーザーがログアウト済みの場合のエッジケースをカバーすること。モックは使わないこと。`                                                                |
| `ログインのバグを直して`   | `セッションタイムアウト後にログインが失敗するとユーザーから報告がある。src/auth/ の認証フロー、特にトークンリフレッシュを確認して。問題を再現する失敗テストを書いてから直すこと。` |
| `ダッシュボードをよくして` | `[スクリーンショットを貼る] このデザインを実装して。実装後にスクリーンショットを撮って元のデザインと比較し、差分を列挙して直すこと。`                                              |

### 5-2. 検証方法を必ず含める

AI は「検証できる」状態だと大幅に品質が上がる。

```
✅ 良い指示の構造:
  1. 何を作るか（タスク定義）
  2. どこを見ればいいか（コンテキスト指定）
  3. どう確認するか（検証方法）

例:
  「validateEmail 関数を実装してくれ。
   テストケース: user@example.com → true, invalid → false, user@.com → false
   実装後にテストを実行して全て通ることを確認して。」
```

### 5-3. 既存パターンを参照させる

```
「既存ウィジェットの実装（HotDogWidget.php が良い例）を参考にして
同じパターンで月選択・年ページネーション付きのカレンダーウィジェットを
ライブラリを新たに追加せず実装して。」
```

## 6. コンテキスト管理（長期タスクの要点）

AI のコンテキストウィンドウは有限で、**満杯になると初期の指示を「忘れる」**。

| 状況                           | 対処法                                                             |
| ------------------------------ | ------------------------------------------------------------------ |
| 無関係なタスクを混ぜてしまった | `/clear` でコンテキストをリセットして再開                          |
| 同じ指摘を2回以上した          | コンテキストが汚染されている。クリアして最初から具体的に指示し直す |
| 長い探索をさせたい             | サブエージェントに探索させて結果だけ受け取る                       |
| セッションをまたぐ大規模作業   | セッションを名前付きで保存し再開する                               |

## 7. よくある失敗パターンと対策

| 失敗パターン                           | 原因                                           | 対策                                                                 |
| -------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------- |
| 指示を無視される                       | `CLAUDE.md` が長すぎて重要ルールが埋もれている | 不要な行を削る。「重要」「MUST」など強調語を使う                     |
| 動かないコードが生成される             | 検証手段がない                                 | テストコマンドを指示に含める。「テストを書いてから実装して」と伝える |
| 想定外の設計になる                     | アーキテクチャ方針が伝わっていない             | 既存の「良い例ファイル」を参照させる                                 |
| 途中で止まる / 方向を間違える          | タスクが大きすぎる                             | フェーズに分けて段階的に指示する                                     |
| セキュリティ的に問題のあるコードが出る | セキュリティ要件が未定義                       | OWASPのリスク（SQLi, XSS等）への対処を指示書に明記する               |

## 8. ゼロからアプリを作らせる指示書テンプレート

新規プロジェクト開始時にそのまま使える雛形。

````markdown
# アプリ仕様書

## 概要
[アプリの目的を1〜2行で説明]

## 機能一覧
- [ ] [機能1]
- [ ] [機能2]
- [ ] [機能3]

## 技術スタック
- フロントエンド: [例: React + TypeScript + Vite]
- バックエンド: [例: Node.js + Express]
- DB: [例: PostgreSQL]
- 認証: [例: JWT]
- インフラ: [例: Docker Compose]

## 画面一覧
1. ログイン画面
2. [画面2]
3. [画面3]

## API 設計
- `GET /api/items` - 一覧取得
- `POST /api/items` - 新規作成
- `PUT /api/items/:id` - 更新
- `DELETE /api/items/:id` - 削除

## データモデル
| フィールド | 型     | 説明   |
| ---------- | ------ | ------ |
| id         | UUID   | 主キー |
| name       | string | 名前   |

## 非機能要件
- レスポンス: 200ms 以内
- 認証: 全 API エンドポイントに JWT 認証
- バリデーション: 入力値は全てサーバー側でバリデーション

## 実装時の制約
- テストを書いてから実装すること（TDD）
- TypeScript の `any` は使用禁止
- シークレット情報はハードコードせず環境変数を使うこと
- SQL インジェクション・XSS 対策を必ず実施すること
````

## 10. まとめ：全自動開発を成功させる3原則

1. **仕様を先に固める**  
   曖昧な状態で実装させない。AI にインタビューさせて `SPEC.md` を作ってから実装へ。

2. **検証方法をセットで渡す**  
   「テストを書いてから実装して」「テストを実行して全部通ることを確認して」を必ず含める。

3. **指示書は短く保つ**  
   `CLAUDE.md` や `AGENTS.md` が長すぎると AI が重要指示を無視する。「なくても AI が正しく動く」内容は削除する。
