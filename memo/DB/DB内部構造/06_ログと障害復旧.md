## この章のゴール

[04章](./04_バッファプールとキャッシュ.md)で見たように、更新されたページはすぐにディスクへ反映されず、メモリ上の「ダーティページ」としてしばらく留まります。では、コミット直後にサーバーの電源が落ちたら、そのデータはどうなるのでしょうか?この疑問に答えるのが**WAL(Write-Ahead Logging、ログ先行書き込み)**の仕組みです。

---

## Write-Ahead Loggingの基本原則

WALの原則は非常にシンプルです。**「データファイル本体を変更する前に、必ずその変更内容をログに書き、ログをディスクに確実に書き込んでからでないと、コミット完了とは言わない」**というルールです。

```
① UPDATE文を実行 → メモリ上のページを変更(まだディスクのデータファイルは古いまま)
② 変更内容を「ログ」としてメモリ上に記録
③ COMMIT時: ログをディスクへ書き込む(fsync) ← ここが完了して初めて「コミット成功」
④ データファイル本体(ダーティページ)は、後でまとめてディスクに書き戻される(チェックポイント時)
```

ポイントは、**重い「ページ全体」の書き込みではなく、軽い「変更差分」のログだけを先にディスクに確実に書き込む**という点です。これにより、コミットのたびに巨大なページ全体を毎回ディスクに書く必要がなくなり、性能と安全性を両立できます。

> PostgreSQLでは、「変更を適用する前に必ずログへ先に書く」というルールにより、クラッシュが発生してもWALを再生することでデータベースを一貫した状態に復元できることが保証されます。コミットが完了したとみなされる前に、PostgreSQLはWALをfsyncでディスクにフラッシュします。これにより、システムがログをディスクに書き込む前にクラッシュしたとしても、永続性が保証されます。(出典: [PostgreSQL公式ドキュメント: Chapter 28. Reliability and the Write-Ahead Log](https://www.postgresql.org/docs/current/wal.html))

> SQL Serverは、ログ先行書き込みアルゴリズム(Write-Ahead Logging)を使用しており、これはデータ変更に対応するログレコードがディスクに書き込まれるまでは、そのデータ変更をディスクに書き込まないことを保証します。ログレコードは、対応するダーティページがバッファキャッシュからディスクにフラッシュされる前に、必ずディスクへ書き込まれなければなりません。もしダーティページを先に書き込んでしまうと、ログレコードが書き込まれる前にサーバーが故障した場合、ロールバックできない変更がディスク上に残ってしまうためです。(出典: [Microsoft Learn: SQL Server Transaction Log Architecture and Management Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-log-architecture-and-management-guide?view=sql-server-ver17))

この原則自体は3製品とも共通しており、業界標準的な考え方です。

---

## チェックポイント

ログはコミットのたびに増え続けるため、無限に保持することはできません。そこで定期的に「この時点までのダーティページは、すべて確実にディスクへ反映しました」という区切りを作ります。これが**チェックポイント**です。

> チェックポイント時には、メモリ上のダーティページ(変更されたデータ)がストレージへ書き戻され、リカバリ時にWALへの依存を減らします。チェックポイントはリカバリの開始地点として機能し、リカバリ時に処理が必要なWALのサイズを削減します。(出典: [PostgreSQL公式ドキュメント: 19.5 Write Ahead Log](https://www.postgresql.org/docs/current/runtime-config-wal.html))

チェックポイント以前のログは、クラッシュリカバリの際にはもう不要になるため、アーカイブや削除の対象にできます(バックアップの仕組みとも関係する重要な概念です)。

---

## クラッシュリカバリの流れ

サーバーが不正終了(電源断・強制終了など)した後、再起動時には次のようなリカバリ処理が自動的に走ります。

1. 最後のチェックポイント以降のログを読み込む。
2. **REDO(再実行)**: ログに記録されている変更のうち、まだディスクに反映されていないものを再適用する。
3. **UNDO(取り消し)**: ログを見て、クラッシュ時点でコミットされていなかったトランザクションの変更を取り消す。

この「REDOで進めてからUNDOで戻す」という2段階の考え方は、多くのRDBMSで共通する古典的なリカバリアルゴリズム(ARIESという手法が有名)の基本形です。

## 製品ごとのログの仕組み

### PostgreSQL: WAL

WALは1本のログストリームとして記録され、`pg_wal` ディレクトリ配下にセグメントファイルとして保存されます。このWALはレプリケーション(ストリーミングレプリケーション)にもそのまま利用される、PostgreSQLのアーキテクチャの中核です。

### MySQL(InnoDB): redo log + undo log

InnoDBは「redo log(再実行ログ、クラッシュ後に変更を再適用するためのログ)」と、[05章](./05_トランザクションと同時実行制御.md)で紹介した「undo log(MVCCとロールバックに使うログ)」の2種類を使い分けます。

> InnoDBのredo logは、クラッシュリカバリ中に不正なデータを修正するために使われるディスクベースのデータ構造です。通常の運用中は、SQL文やロウレベルAPIの呼び出しによるデータ変更を記録するためにエンコードされます。予期せぬシャットダウン前に完了しなかった変更は、起動時に自動的に再現されます。(出典: [MySQL公式ドキュメント: 17.6.5 Redo Log](https://dev.mysql.com/doc/refman/8.0/en/innodb-redo-log.html))

### SQL Server: トランザクションログ(VLF)

SQL Serverのトランザクションログは、内部的に**VLF(Virtual Log File)**という単位に分割されており、1つのログブロックには複数の同時実行トランザクションのログレコードが混在して記録されます。

> 各トランザクションログレコードには、変更を行ったトランザクションのID、そのトランザクションの開始・終了時刻、変更されたページ、実際のデータ変更内容などの詳細が含まれます。(出典: [Microsoft Learn: SQL Server Transaction Log Architecture and Management Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-log-architecture-and-management-guide?view=sql-server-ver17))

## 壊れたページ問題とその対策

WALには一つ弱点があります。「ログはページの**差分**しか記録しない」ため、もしディスクへの書き込み中にOSやストレージがクラッシュし、ページ自体が「新旧データが混ざった中途半端な状態(torn page、壊れたページ)」になってしまうと、差分ログだけではそのページを正しく復元できません。

> ページサイズが16KBの場合でも、OSの書き込み単位はしばしばそれより小さい(4KBなど)ため、書き込み中にMySQLがクラッシュすると、ディスク上のページが新旧データの混合になってしまう「torn page(破損ページ)」が発生する可能性があります。redo logはベースとなるページ自体が壊れている場合は復旧できません(redo logは既存のページデータの上に変更を適用する仕組みのため)。(出典: [MySQL公式ドキュメント: 17.6.4 Doublewrite Buffer](https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html))

これに対する各製品の対策は以下の通りです。

- **MySQL(InnoDB)**: **ダブルライトバッファ**という仕組みを使い、実際のページ更新前に、まずページのコピーを別の連続領域へ書き込んでおきます。クラッシュ時はこのコピーから正しいページを復元します。
- **PostgreSQL**: `full_page_writes` というオプション(既定でON)により、チェックポイント後の最初の更新時にはページ全体をWALに書き込みます。差分ではなくページ全体があるので、壊れたページでも正しい状態を復元できます。

> `full_page_writes` を有効にしている場合、PostgreSQLはチェックポイント後の最初の変更時に、各ディスクページの内容全体をWALへ書き込みます。これは、OSクラッシュの際に書き込み途中だったページが部分的にしか完了していない可能性があるために必要な仕組みです。(出典: [PostgreSQL公式ドキュメント: 28.5 WAL Configuration](https://www.postgresql.org/docs/current/wal-configuration.html))

- **SQL Server**: ページの末尾に「トーンビット(torn page detection)」やチェックサムを持たせ、破損を検知します。破損自体を未然に防ぐダブルライト的な仕組みとしては「間接チェックポイント」やストレージ側のI/O保証に依存する設計です。

## 製品ごとの違いまとめ

| 観点 | PostgreSQL | MySQL(InnoDB) | SQL Server |
|---|---|---|---|
| ログの名称 | WAL(Write-Ahead Log) | redo log + undo log(役割分担) | トランザクションログ(VLF単位) |
| 壊れたページ対策 | full_page_writes(差分ではなくページ全体を記録) | ダブルライトバッファ(先にコピーへ退避) | チェックサム/torn page detectionによる検知 |
| ログとレプリケーションの関係 | WALをそのままストリーミングレプリケーションに利用 | binlog(バイナリログ)という別のログをレプリケーションに使用することが多い | トランザクションログをAlways On可用性グループ等で転送 |
| チェックポイントの主な設定 | `checkpoint_timeout` / `checkpoint_completion_target` | `innodb_log_file_size` 等 | 自動チェックポイント/間接チェックポイント |
