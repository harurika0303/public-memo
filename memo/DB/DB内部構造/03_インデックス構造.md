## この章のゴール

[02章](./02_ストレージとページ構造.md)で「1行を読むにもページ単位で読み込む」ことを学びました。インデックスがなければ、目的の1行を探すために**テーブル全体のページを先頭から順に読む**しかありません(これを「フルスキャン」「テーブルスキャン」と呼びます)。この章では、この探索を高速化する仕組みである**インデックス**、特に最も基本的な**B-Tree**を理解します。

---

## なぜインデックスが必要か

たとえ話として、辞書を思い浮かべてください。

- **インデックスがない状態** = ページの並び順がバラバラな辞書。「あ」から始まる単語を探すために、1ページ目から最後のページまで全部めくる必要がある。
- **インデックスがある状態** = 「あいうえお順」に並んだ索引(インデックス)を使い、目的のページまで一気に飛べる。

RDBのテーブルも、行の物理的な並び順は必ずしも検索したい順序と一致しません。そこで、検索したいカラム(例: `id` や `email`)の値と、その行が格納されている場所を対応付けた「索引」を別途作っておくのがインデックスです。

## B-Treeの仕組み

RDBで最も標準的に使われるインデックス構造が **B-Tree(バランス木)** です。3製品とも、特に指定がなければB-Tree系のインデックスが作成されます。

> PostgreSQLでは `CREATE INDEX` コマンドはデフォルトでB-Treeインデックスを作成します。これはほとんどのケースに適しており、等価比較(`=`)や範囲比較(`<`, `>`, `BETWEEN`など)ができるデータに対して、プランナが自動的にB-Treeインデックスの利用を検討します。(出典: [PostgreSQL公式ドキュメント: Index Types](https://www.postgresql.org/docs/current/indexes-types.html), [PostgreSQL公式ドキュメント: B-Tree Indexes](https://www.postgresql.org/docs/current/btree.html))

B-Treeは、次のような「根(ルート)」「枝(中間ノード)」「葉(リーフノード)」からなる木構造です。

```
                [ルートページ]
                 M ?
              /       \
      [中間ページ]        [中間ページ]
       A〜L               N〜Z
      /    \             /     \
  [葉]     [葉]        [葉]     [葉]
  A-F      G-L         N-S      T-Z
  (行の場所)  (行の場所)  (行の場所) (行の場所)
```

- 探索は必ずルートから始まり、値の範囲に応じて左右どちらに進むかを判断しながら下に降りていきます。
- どの葉ノードまでも「根からの距離」がほぼ同じ(=平衡している)ため、テーブルの行数が100万行でも1億行でも、木の深さは数段しか変わらず、探索は高速なまま保たれます。これが「バランス木」と呼ばれる理由です。
- 葉ノード同士は横にリンクされており、範囲検索(`BETWEEN` など)のときは葉ノードを横に辿るだけで済みます。

> SQL Serverのクラスタ化・非クラスタ化インデックスは、いずれもルート・中間ノード・葉から構成されるB+ツリーとして構成されています。(出典: [Microsoft Learn: Clustered and Nonclustered Indexes Described](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17))

## クラスタ化インデックス vs セカンダリ(非クラスタ化)インデックス

ここが3製品で最も設計思想が分かれるポイントです。ポイントは「**テーブルの行そのものの並び順を、インデックスがコントロールしているか**」です。

### MySQL(InnoDB)とSQL Server: テーブルの実体=クラスタ化インデックスの葉

MySQL(InnoDB)とSQL Serverでは、テーブルの行データそのものが、ある1つのインデックス(クラスタ化インデックス、多くの場合は主キー)の葉ノードとして物理的に格納されます。つまり「テーブル」と「主キーのインデックス」がほぼ一体化しています。

> InnoDBの各テーブルには、行データそのものを格納する「クラスタ化インデックス」という特別なインデックスがあります。通常、クラスタ化インデックスは主キーと同一であり、`PRIMARY KEY` を定義すると、InnoDBはそれをクラスタ化インデックスとして使用します。主キーを定義しない場合、InnoDBはNOT NULL制約を持つ最初の一意インデックスを使用し、それも無ければ行ID(ROWID)を持つ隠しクラスタ化インデックス(`GEN_CLUST_INDEX`)を生成します。クラスタ化インデックス以外のインデックスは「セカンダリインデックス」と呼ばれ、各レコードは対象カラムの値に加えて主キーの値を保持します。セカンダリインデックスで検索した後、この主キー値を使ってクラスタ化インデックスから実際の行を取得します(この2段階の検索を「キーの二重引き」と呼ぶことがあります)。(出典: [MySQL公式ドキュメント: Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.0/en/innodb-index-types.html))

> SQL Serverのクラスタ化インデックスは、キー値に基づいてデータ行を並べ替えて格納し、その葉ノード自体がテーブルのデータページになります。1つのテーブルにつきクラスタ化インデックスは1つしか作れません(行の物理的な並び順は1通りしかあり得ないため)。非クラスタ化インデックスも同じB-Tree構造を持ちますが、葉ノードにはデータ行ではなく、実データへのポインタ(行ロケータ)が格納されます。(出典: [Microsoft Learn: Clustered and Nonclustered Indexes Described](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17))

### PostgreSQL: すべてのインデックスがセカンダリインデックス

PostgreSQLには、上記のような「クラスタ化インデックス」の概念がありません。テーブルの行データは「ヒープ」と呼ばれる、特に順序を持たない領域に格納され、インデックスは常にヒープ上の行の物理的な位置(TID)を指す「別テーブル」として存在します。

> PostgreSQLのすべてのインデックスは「セカンダリインデックス」です。つまり、各インデックスはテーブルの主要なデータ領域(PostgreSQLでは「ヒープ」と呼ばれる)とは別に格納されます。PostgreSQLは他のRDBMSにある「クラスタ化インデックス」による行の自動的な物理順序付けをサポートしていません。(出典: [PostgreSQL公式ドキュメント: Index Types](https://www.postgresql.org/docs/current/indexes-types.html))

- 例外として `CLUSTER` コマンドを使うと、その時点で指定したインデックス順に物理的に並べ替えることは**1回限りの操作として**可能ですが、以降の更新で自動的に順序が維持されるわけではありません(MySQL/SQL Serverのクラスタ化インデックスのように「常に並び順が保たれる」わけではない、という違いに注意してください)。

### イメージ図での比較

```
[MySQL(InnoDB) / SQL Server: クラスタ化インデックスあり]
  主キーインデックス(B-Tree)の葉 = そのままテーブルの行データ
  セカンダリインデックスの葉 = 主キー値 or 行ロケータ(→ 主キー経由で実データへ)

[PostgreSQL: クラスタ化インデックスなし]
  ヒープ(順序を持たないただの行の集まり)
  インデックスの葉 = 行の物理位置(TID) を指すだけの別データ構造
```

## 製品ごとのインデックス構造の違い

| 観点 | PostgreSQL | MySQL(InnoDB) | SQL Server |
|---|---|---|---|
| クラスタ化インデックス | なし(すべてセカンダリ) | あり(通常は主キー、なければ暗黙的に生成) | あり(任意、作らなければヒープテーブルになる) |
| セカンダリインデックスが指す先 | ヒープの物理位置(TID) | クラスタ化インデックスのキー値(主キー) | 行ロケータ(クラスタ化インデックスのキー、またはヒープのRID) |
| 主キーを長くすることの影響 | セカンダリインデックスのサイズには影響しない | 全セカンダリインデックスが主キー値を保持するため、サイズが肥大化しやすい | 全非クラスタ化インデックスが行ロケータを保持するため、同様にサイズへ影響 |
| デフォルトのインデックス種別 | B-Tree | B-Tree(InnoDBの主要な索引方式) | B-Tree(行ストア) |

## カバリングインデックス(Index-Only Scan)

SELECTで取得したいカラムがすべてインデックス自体に含まれている場合、テーブル本体(ヒープ/クラスタ化インデックス)へアクセスせず、インデックスだけで結果を返せることがあります。これを**カバリングインデックス**、実行時の動作を**Index-Only Scan**と呼びます。

> インデックスに含まれる列だけで問い合わせが完結する場合、PostgreSQLはテーブル本体を読まずにインデックスだけでスキャンを完了できます。これを「Index-Only Scan」と呼びます。(出典: [PostgreSQL公式ドキュメント: Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html))

MySQL・SQL Serverにも同様の概念があり、SQL Serverでは非クラスタ化インデックスに「INCLUDE列」を追加することでカバリングインデックスを意図的に設計できます。

---

## まとめ

- インデックスの多くはB-Tree構造で、根から葉まで一定の深さでたどり着けるため、大量データでも高速に検索できる。
- MySQL(InnoDB)・SQL Serverは「クラスタ化インデックス=テーブルの実体」という考え方を持つが、PostgreSQLはテーブル(ヒープ)とインデックスが完全に別物として管理される。この違いは、主キー設計の指針(短い主キーを選ぶべきか等)にも影響する。
