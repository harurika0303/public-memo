## この章のゴール

複数のユーザーが同時に同じテーブル、同じ行にアクセスしたとき、DBはどうやって「データが壊れない」ようにしているのかを理解します。ここがRDBの内部構造の中でも最も奥が深く、かつ製品ごとの違いが大きい領域です。

---

## ACID特性のおさらい

トランザクション(複数のSQL操作をひとかたまりとして扱う単位)が満たすべき性質として、**ACID**という頭字語がよく使われます。

| 頭文字 | 名前 | 意味 |
|---|---|---|
| A | Atomicity(原子性) | トランザクション内の操作は「全部成功」か「全部失敗(ロールバック)」のどちらかになる |
| C | Consistency(一貫性) | トランザクション前後でデータが制約(外部キー等)に違反しない |
| I | Isolation(独立性) | 同時実行される他のトランザクションの影響を(設定した分離レベルの範囲で)受けない |
| D | Durability(永続性) | コミットが完了したデータは、電源断が起きても失われない |

このうち **D(永続性)** は次章の[06_ログと障害復旧](./06_ログと障害復旧.md)、**I(独立性)** はこの章のテーマです。

## 同時実行が引き起こす問題と分離レベル

複数のトランザクションが同時に動くと、以下のような問題が起こり得ます。

- **ダーティリード**: あるトランザクションが、まだコミットされていない(=ロールバックされるかもしれない)他のトランザクションの変更を読んでしまう。
- **反復不能読み取り(Non-repeatable Read)**: 同じトランザクション内で同じ行を2回読んだら、間に他のトランザクションがコミットした変更のせいで結果が変わってしまう。
- **ファントムリード**: 同じ条件で2回検索したら、間に他のトランザクションが挿入した行のせいで件数が変わってしまう。

これらをどこまで許容するかを段階的に定義したものが、SQL標準の**トランザクション分離レベル**です。

| 分離レベル | ダーティリード | 反復不能読み取り | ファントムリード |
|---|---|---|---|
| READ UNCOMMITTED | 起こりうる | 起こりうる | 起こりうる |
| READ COMMITTED | 防止 | 起こりうる | 起こりうる |
| REPEATABLE READ | 防止 | 防止 | 起こりうる(製品によっては防止) |
| SERIALIZABLE | 防止 | 防止 | 防止 |

**重要な注意点**: 分離レベルの「名前」は標準化されていますが、**その名前が実際に何を保証するかは製品ごとに実装が異なります**。特にPostgreSQLはMVCCの仕組み上、REPEATABLE READでもファントムリードが標準の定義以上に強く防止されます。

## ロック方式 vs MVCC方式

同時実行制御には、大きく分けて2つのアプローチがあります。

1. **ロック方式(悲観的並行性制御)**: 読み書きのたびに対象データにロックをかけ、競合する操作を待たせる。「読み取り」も対象に共有ロックをかけるため、**読み取りが書き込みをブロックし、書き込みが読み取りをブロックする**ことがある。
2. **MVCC方式(多版型同時実行制御、楽観的な要素が強い)**: 行が更新されるたびに「古いバージョン」を残しておき、各トランザクションは自分の開始時点(またはステートメント開始時点)の「スナップショット」に対応するバージョンを読む。これにより**読み取りは書き込みをブロックせず、書き込みも読み取りをブロックしない**。

> PostgreSQLはMVCCを使用しており、各SQL文はある時点でのデータのスナップショットを見ます。これにより、同時実行中の他のトランザクションによって作られた不整合なデータを見ることを防ぎ、トランザクションの独立性を提供します。最大の利点は、データ読み取りのために獲得するロックが、データ書き込みのために獲得するロックと競合しないことです。読み取りは決して書き込みをブロックせず、書き込みも決して読み取りをブロックしません。(出典: [PostgreSQL公式ドキュメント: 13.1 Introduction (MVCC)](https://www.postgresql.org/docs/current/mvcc-intro.html))

PostgreSQLとMySQL(InnoDB)はどちらもMVCCを採用していますが、**SQL Serverは既定でロック方式**であり、MVCC的な仕組み(行バージョニング)はオプションとして有効化する形になっている点が大きな違いです。

---

## MVCCの仕組み: PostgreSQLの場合

PostgreSQLは、行(タプル)が更新されるたびに、古いバージョンをそのまま残し、新しいバージョンを別の行として追加します(DELETEも実際には物理削除せず「無効」のマークを付けます)。各行には、その行を作った/消したトランザクションIDが記録されており、各トランザクションは「自分が見てよいバージョンはどれか」をこの情報とスナップショットで判断します。

> PostgreSQLは3つの分離レベルをサポートしています: READ COMMITTED、REPEATABLE READ、SERIALIZABLEです。READ COMMITTEDは文ごとにスナップショットを取得するため、一般的なOLTPワークロードに適しています。REPEATABLE READはトランザクション全体でスナップショットを固定し、トランザクション開始時点の一貫したスナップショットを取得します。SERIALIZABLEは、SSI(Serializable Snapshot Isolation)による競合検出を追加した、最も厳格な分離レベルです。(出典: [PostgreSQL公式ドキュメント: Chapter 13. Concurrency Control](https://www.postgresql.org/docs/current/mvcc.html))

不要になった古いバージョンの行は自動削除されず溜まっていくため、`VACUUM` という仕組みで定期的に回収する必要があります。これはPostgreSQL特有の運用ポイントで、VACUUMが追いつかないと、テーブルが不要な古いバージョンで肥大化する「テーブル膨張(bloat)」が起こります。

---

## MVCCの仕組み: MySQL(InnoDB)の場合

InnoDBもMVCCを採用していますが、実装方法がPostgreSQLとは異なります。行を直接更新し、更新前の内容は**アンドゥログ(undo log)**という別領域に退避させる方式です。

> InnoDBのMVCC実装において、アンドゥログは重要な役割を果たします。過去のバージョンのデータを保持し、トランザクションのロールバックと多版性(マルチバージョニング)をサポートする責任を持ちます。トランザクション内で行が変更されるたびに、InnoDBは新しいバージョンを生成し、それをアンドゥログに保存します。(出典: [MySQL公式ドキュメント: 17.3 InnoDB Multi-Versioning](https://dev.mysql.com/doc/refman/8.0/en/innodb-multi-versioning.html))

InnoDBの既定の分離レベルは **REPEATABLE READ** です(PostgreSQLやSQL Serverの既定であるREAD COMMITTEDとは異なる点に注意してください)。この分離レベルは「スナップショットをトランザクション開始時(正確には最初の読み取りクエリ実行時)に1回だけ取得し、トランザクション終了まで固定する」という考え方に基づいています。加えてInnoDBは、この分離レベルでもファントムリードを防ぐために、次に説明する**ネクストキーロック**という仕組みを併用しています。

---

## SQL Serverの場合: 既定はロック方式、RCSIで行バージョニングへ

SQL Serverは既定では**ロックベース**の同時実行制御を行います。既定の分離レベルはREAD COMMITTEDですが、これは「共有ロックを使ったREAD COMMITTED」であり、PostgreSQL/MySQLのようなMVCCベースのREAD COMMITTEDとは仕組みが異なります(読み取りが書き込みをブロックし得ます)。

ただしSQL Serverには、オプションとして有効化できる**行バージョニングベースの分離レベル**が用意されています。

> RCSI(Read Committed Snapshot Isolation)は、分離レベルとしては論理的に「Read Committed」のままですが、読み取りに共有ロックを使う代わりに行バージョニングを使って実装されます。RCSIはステートメントレベルのスナップショット分離であり、クエリは各ステートメント開始時点での最新のコミット済みの値を参照します。行バージョニングを使う場合、読み取りは書き込みをブロックせず、書き込みも読み取りをブロックしません(ただし書き込み同士は引き続きロックし合います)。変更された行の旧バージョンを保存する領域はtempdb内の「バージョンストア」と呼ばれます。(出典: [Microsoft Learn: Transaction Locking and Row Versioning Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver17))

さらに厳密な `SNAPSHOT` 分離レベルも用意されており、こちらはトランザクション開始時点のスナップショットを固定します(PostgreSQL/MySQLのREPEATABLE READに近い挙動)。

> RCSIを有効化することは、最適化されたロック(Optimized Locking)と組み合わせて、多くのケースで最も効率的な選択として推奨されています。(出典: [Microsoft Learn: Optimized Locking](https://learn.microsoft.com/en-us/sql/relational-databases/performance/optimized-locking?view=sql-server-ver17))

つまりSQL Serverは「**MVCCを使うかどうかを選べる**」という設計であり、PostgreSQL/MySQLのように「常にMVCCが土台にある」わけではない点が最大の違いです。

## 明示的ロックの種類

MVCCを使っていても、書き込み同士の競合を防ぐためにロックそのものは必要です。ここでは各製品のロックの基本単位を紹介します。

### PostgreSQL

> PostgreSQLのすべてのロックモードは、名前に「row」という単語が含まれていても、実質的にはテーブルレベルのロックです(名前は歴史的経緯によるものです)。ACCESS SHARE、ROW SHARE、ROW EXCLUSIVE、SHARE UPDATE EXCLUSIVE、SHARE、SHARE ROW EXCLUSIVE、EXCLUSIVE、ACCESS EXCLUSIVEという8種類のテーブルレベルロックモードに加え、行レベルロックも存在します。(出典: [PostgreSQL公式ドキュメント: 13.3 Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html))

### MySQL(InnoDB): ネクストキーロック

InnoDBは、単純な行ロックに加えて、行と行の「隙間(ギャップ)」に対してもロックをかける独自の仕組みを持っています。これはREPEATABLE READでファントムリードを防ぐための重要な機能です。

> レコードロックは1つのレコードに対するロックです。ギャップロックは、あるレコードとその直前のレコードの間の範囲(隙間)に対するロックで、その隙間へのINSERTを防ぐために使われます。ネクストキーロックは、インデックスレコードへのロックと、そのレコードの直前の隙間に対するギャップロックを組み合わせたものです。InnoDBは既定で、検索やインデックススキャンにこのネクストキーロックを使用し、ファントムリードを防ぎます。(出典: [MySQL公式ドキュメント: 17.7.1 InnoDB Locking](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html))

### SQL Server: 意図ロック(Intent Lock)と更新ロック(U)

SQL Serverは階層構造(データベース→テーブル→ページ→行)を持つロックの世界で、上位レベルに「この下でロックを取ろうとしている」ことを示す**意図ロック**を使い、効率的な競合チェックを行います。

> 行に対する排他ロックを取得するには、トランザクションはまずそのページに対する意図排他ロック(IX)を取得し、さらにそのページを含むオブジェクトに対しても意図排他ロックを取得する必要があります。意図ロックの目的は、より上位のレベルで非互換なロック要求を効率的に検出し、非互換なロックが許可されるのを防ぐことです。(出典: [Microsoft Learn: Transaction Locking and Row Versioning Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver17))

また、共有ロック(S)から排他ロック(X)への昇格待ちで発生しやすいデッドロックを避けるため、**更新ロック(U)**という中間的なロックモードも用意されています。

## デッドロック

デッドロックは、2つ以上のトランザクションが互いに相手の持つロックの解放を待ち続け、永遠に進めなくなる状態です。

```
トランザクションA: 行1をロック → 行2のロック待ち
トランザクションB: 行2をロック → 行1のロック待ち
   → 互いに待ち続けて先に進めない(デッドロック)
```

3製品とも、デッドロックを検知する仕組みを内蔵しており、検知すると片方のトランザクションを強制的にロールバックさせてもう片方を先に進めます(ロールバックされる側は、通常「処理コストが小さい方」などの基準で選ばれます)。アプリケーション側では、デッドロックが発生した場合にリトライする実装が必要です。

## 製品ごとの違いまとめ

| 観点 | PostgreSQL | MySQL(InnoDB) | SQL Server |
|---|---|---|---|
| 既定の分離レベル | READ COMMITTED | REPEATABLE READ | READ COMMITTED(ロックベース) |
| 同時実行制御の土台 | 常にMVCC | 常にMVCC | 既定はロック、RCSI/SNAPSHOTでMVCC的挙動を選択可 |
| 旧バージョンの保存場所 | テーブル自身の中(同じヒープ内に新旧バージョンが同居) | アンドゥログ(専用領域) | tempdbのバージョンストア(RCSI/SNAPSHOT利用時) |
| 不要になった旧バージョンの回収 | VACUUM(手動・自動) | パージスレッドが自動処理 | tempdb内で自動的に世代管理 |
| ファントムリード対策 | スナップショットの仕組み自体で対応 | ネクストキーロック(ギャップロック含む) | ロックの範囲拡張、またはSNAPSHOT分離レベル |
| 特徴的なロック概念 | テーブルロック8種+行ロック | レコードロック/ギャップロック/ネクストキーロック | 意図ロック(IS/IX/SIX)、更新ロック(U) |
