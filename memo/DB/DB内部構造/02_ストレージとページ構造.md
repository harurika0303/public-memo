## この章のゴール

「テーブルにデータを入れる」と言うと簡単に聞こえますが、実際にはディスク上の**ファイル**の中に、**固定サイズの「ページ」**という箱が並んでいて、その箱の中に行のデータが詰め込まれています。この物理的な仕組みを理解することが、インデックスやパフォーマンスチューニングを理解する土台になります。

---

## たとえ話: DBはルーズリーフノート

DBのストレージを、大量のルーズリーフノートに例えるとイメージしやすくなります。

- **ファイル** = 1冊のノート(1冊に入りきらなければ2冊目、3冊目…と分割される)
- **ページ(ブロック)** = ノートの1ページ(サイズが固定されている。だいたい8KBや16KB)
- **行(レコード)** = 1ページの中に書き込まれた1件分のメモ
- **インデックス** = ノートの内容とは別に作る「索引カード」(詳細は [03章](./03_インデックス構造.md))

DBはこのノートを1ページ単位で読み書きします。1行だけ読みたくても、実際には「その行が載っているページ全体」をディスクから読み込みます。これが、インデックスの有無でパフォーマンスが大きく変わる理由の一つです。

---

## ファイルの階層構造

どの製品も、大まかには次のような階層でデータを管理しています。

```
データベース
 └─ テーブルスペース(データを物理的にどこに置くかのグループ)
     └─ テーブル / インデックス
         └─ ファイル(1つ以上に分割されることがある)
             └─ ページ(固定サイズのブロック)
                 └─ 行(レコード)
```

- **テーブルスペース**という考え方は3製品とも存在しますが、使われ方の重みが異なります。PostgreSQLとSQL Serverは「どのディスクにファイルを配置するか」を制御するための仕組みという位置づけが強く、MySQL(InnoDB)はデフォルトで全テーブルが1つの共有テーブルスペース(`ibdata1`)やテーブルごとのファイル(`innodb_file_per_table`)に格納されます。

---

## ページ(ブロック)という単位

DBはディスクI/Oを、**ページ(ブロック)**と呼ばれる固定サイズの単位でまとめて行います。1バイトだけ読みたい場合でも、そのバイトが含まれるページ全体を読み込みます。

> PostgreSQLでは、テーブルもインデックスも「ページ」という単位でファイルに格納されます。ページのヘッダーに続いて、各行の位置を示す「アイテム識別子(ItemIdData)」が4バイトずつ並び、実際の行データはページの後方から詰められていきます。(出典: [PostgreSQL公式ドキュメント: Database Page Layout](https://www.postgresql.org/docs/current/storage-page-layout.html))

> MySQL(InnoDB)のバッファプールは固定サイズのページに分割されており、デフォルトのページサイズは16KBです。(出典: [MySQL公式ドキュメント: Buffer Pool](https://dev.mysql.com/doc/refman/8.0/en/innodb-buffer-pool.html))

> SQL Serverにおいて、ページはデータベースエンジンにおける基本的なデータ保存単位です。データファイル(.mdf/.ndf)に割り当てられたディスク空間は、0からnまでの連続したページ番号で論理的に分割管理されます。また8ページ分の物理的に連続した領域を「エクステント」と呼び、ページの割り当て管理を効率化しています。(出典: [Microsoft Learn: Pages and Extents Architecture Guide](https://learn.microsoft.com/en-us/sql/relational-databases/pages-and-extents-architecture-guide?view=sql-server-ver17))

### ページサイズの比較

| 製品 | デフォルトページサイズ | 変更可否 |
|---|---|---|
| PostgreSQL | 8KB | ソースからのビルド時のみ変更可(運用中の変更は基本不可) |
| MySQL(InnoDB) | 16KB | `innodb_page_size` でインスタンス作成時に指定可能(4KB〜64KB) |
| SQL Server | 8KB | 変更不可(固定) |

ページサイズが大きいほど、1回のI/Oでまとめて読める行数は増えますが、無駄なデータまで読み込む可能性(オーバーフェッチ)も増える、というトレードオフがあります。

## ページの中身: 1行(タプル/レコード)はどう入っているか

ページの中身は、おおよそ「ヘッダー」「行のインデックス(オフセット一覧)」「実際の行データ」の3つで構成されるという考え方は共通しています。

```
┌─────────────────────────────┐
│ ページヘッダー(空き容量などの管理情報) │
├─────────────────────────────┤
│ 行オフセット一覧(どこに何行目があるか)   │ → ページ先頭から積み上がる
├─────────────────────────────┤
│              (空き領域)              │
├─────────────────────────────┤
│ 実際の行データ(3行目)                │
│ 実際の行データ(2行目)                │ ← ページ末尾から積み上がる
│ 実際の行データ(1行目)                │
└─────────────────────────────┘
```

> PostgreSQLの行(ヒープタプル)は、すべて同じ形式を持ちます。ほとんどの環境で23バイトの固定長ヘッダーがあり、続いてオプションのNULLビットマップ、オプションのオブジェクトIDフィールド、そしてユーザーデータが続きます。(出典: [PostgreSQL公式ドキュメント: Database Page Layout](https://www.postgresql.org/docs/current/storage-page-layout.html))

MySQL(InnoDB)の行には、通常のカラムに加えて内部管理用の隠しカラムが付与されます。これは [05章](./05_トランザクションと同時実行制御.md) で説明するMVCC(多版型同時実行制御)の実現に使われます。

> InnoDBは、データベースに格納される各行に内部的に3つのフィールドを追加します。6バイトの `DB_TRX_ID` はその行を最後に挿入・更新したトランザクションのIDを示し、7バイトの `DB_ROLL_PTR`(ロールポインタ)はアンドゥログレコードを指し示します。(出典: [MySQL公式ドキュメント: InnoDB Multi-Versioning](https://dev.mysql.com/doc/refman/8.0/en/innodb-multi-versioning.html))

## 大きなデータはどうするか(可変長データの扱い)

長いテキストやBLOBなど、1ページに収まらないほど大きなデータをどう扱うかも製品ごとに工夫が異なります。

- **PostgreSQL**: `TOAST`(The Oversized-Attribute Storage Technique)という仕組みで、大きな値を自動的に圧縮・別テーブルへの分割格納をします。
- **MySQL(InnoDB)**: 行が非常に大きい場合、可変長カラムの一部を「オーバーフローページ」に逃がします。
- **SQL Server**: `ROW_OVERFLOW_DATA` や `LOB_DATA` という別のページ種別に、収まりきらないデータを格納します。

いずれも「1行は基本的に1ページに収める。収まらない分だけ外部に逃がす」という考え方は共通しています。

## 製品ごとの違いまとめ

| 観点 | PostgreSQL | MySQL(InnoDB) | SQL Server |
|---|---|---|---|
| ページ(ブロック)サイズ | 8KB | 16KB(既定) | 8KB(固定) |
| 行の物理的な並び順の制御 | 基本的にできない(後述の[03章](./03_インデックス構造.md)参照) | クラスタ化インデックス(主キー順)で制御 | クラスタ化インデックスで制御(任意) |
| 大きなデータの扱い | TOAST | オーバーフローページ | ROW_OVERFLOW_DATA / LOB_DATA |
| 更新時の行の扱い | 新しいバージョンの行を追記(旧行は後で回収=VACUUM、[05章](./05_トランザクションと同時実行制御.md)参照) | 該当ページ内で更新し、旧イメージはアンドゥログへ退避 | 該当ページ内で更新し、旧イメージはtempdbのバージョンストアへ退避(RCSI利用時) |
