## この章のゴール

ディスク(特にHDD、そしてSSDであっても)へのアクセスは、メモリへのアクセスに比べて桁違いに遅いです。そこでDBは、一度読んだページをメモリ上に保持しておき、次回以降は**ディスクを読まずにメモリから返す**仕組みを持っています。これが**バッファプール(バッファキャッシュ)**です。

---

## なぜメモリキャッシュが必要か

[02章](./02_ストレージとページ構造.md)で見た通り、DBはページ単位でディスクを読み書きします。もし毎回のSELECT文でディスクへ直接アクセスしていたら、性能は大きく落ち込みます。

そこでDBサーバー起動時に、メモリ上に「ページを保持しておくための領域」をあらかじめ確保します。これがバッファプールです。SELECTやUPDATEは、まずこのバッファプール上にページがあるか確認し、なければディスクから読み込んでバッファプールに載せてから処理します。

```
SQL実行 → バッファプールにページがある? 
            ├─ Yes (キャッシュヒット) → そのままメモリ上のデータを使う(高速)
            └─ No  (キャッシュミス)  → ディスクから読み込み、バッファプールに格納 → 使う(低速)
```

このキャッシュヒット率(ヒット率)を高く保つことが、DB性能チューニングの基本的な指標のひとつです。

---

## バッファプールの基本動作

> InnoDBのバッファプールは、テーブルやインデックスへのアクセスをメモリ上でキャッシュするための、InnoDBにおけるメインのメモリ領域です。データページ・インデックスページ・アンドゥログ・データディクショナリなどを保持します。バッファプールは固定サイズのページ(既定16KB)に分割されて管理されます。(出典: [MySQL公式ドキュメント: Buffer Pool](https://dev.mysql.com/doc/refman/8.0/en/innodb-buffer-pool.html))

> SQL Serverのバッファ管理コンポーネントは、データベースページへのアクセス・更新を担う「バッファマネージャー」と、データベースファイルI/Oを削減するための「バッファキャッシュ(バッファプール)」の2つの仕組みで構成されます。バッファは8KBページとして管理され、これはデータページ・インデックスページと同じサイズです。(出典: [Microsoft Learn: Memory Management Architecture Guide](https://learn.microsoft.com/en-us/sql/relational-databases/memory-management-architecture-guide?view=sql-server-ver17))

PostgreSQLも `shared_buffers` というパラメータで指定されたメモリ領域を、同じ目的のバッファプールとして使用します。ただしPostgreSQLは伝統的に「シンプルさ」を重視する設計思想から、**OS自体が持つファイルキャッシュ(ページキャッシュ)を積極的に併用する**前提のチューニングがされている点が特徴です(そのため `shared_buffers` の推奨値は物理メモリの25%程度など、OSキャッシュとの共存を前提とした値になっています)。

## 追い出しアルゴリズム(LRU)

バッファプールのサイズには上限があるため、メモリが満杯になったら「どのページをメモリから追い出すか」を決める必要があります。基本的な考え方は**LRU(Least Recently Used、最も長く使われていないものから追い出す)**です。

> InnoDBのバッファプールは、LRUアルゴリズムの改良版を使ったリストとして管理されています。バッファプールに新しいページを追加する領域が必要な場合、最も長く使われていないページが追い出され、新しいページはリストの「中間」に追加されます。このリストは2つの副リストとして扱われます: 先頭側には最近アクセスされた「新しい(young)」ページの副リスト、末尾側にはあまりアクセスされていない「古い(old)」ページの副リストです。InnoDBがページを読み込む際は、まずこの中間点(oldサブリストの先頭)に挿入され、既定では、クエリによって読み込まれたページは即座に新しいサブリストへ移動するため、バッファプール内に長く留まりやすくなります。(出典: [MySQL公式ドキュメント: Buffer Pool](https://dev.mysql.com/doc/refman/8.0/en/innodb-buffer-pool.html))

このような「単純な末尾/先頭ではなく中間に挿入する」工夫は、たとえば `SELECT * FROM huge_table` のような一括スキャンが走ったときに、それまでキャッシュされていた「本当によく使われるページ」が一気に追い出されてしまう事態(キャッシュ汚染)を防ぐための設計です。PostgreSQLも同様の問題を避けるため、独自の「クロックスイープ」というアルゴリズムでバッファの追い出しを管理しています。

## 製品ごとのキャッシュ構造の違い

| 観点 | PostgreSQL | MySQL(InnoDB) | SQL Server |
|---|---|---|---|
| 主なパラメータ名 | `shared_buffers` | `innodb_buffer_pool_size` | 最大サーバーメモリ(`max server memory`)の範囲内で自動管理 |
| OSキャッシュとの関係 | OSページキャッシュとの二重キャッシュを前提に設計 | 基本的にOSキャッシュに頼らずInnoDB自身で完結させる思想 | OSキャッシュとの二重化は限定的、SQL Serverが積極的に確保 |
| 追い出しアルゴリズム | クロックスイープ(LRU派生) | LRU派生(young/oldサブリスト方式) | LRU-K派生のコスト考慮型アルゴリズム |
| 拡張の仕組み | なし(メモリのみ) | なし(メモリのみ) | バッファプール拡張(NVMe/SSDをバッファの延長として利用可能) |

## ダーティページと書き戻し

バッファプール上のページがUPDATE等で変更されると、そのページはディスク上の内容と一致しなくなります。この状態のページを**ダーティページ**と呼びます。ダーティページは即座にディスクへ書き戻されるわけではなく、後述の[06章](./06_ログと障害復旧.md)で説明する**チェックポイント**のタイミングなどでまとめてディスクに書き戻されます。

これにより「同じページに対する複数回の更新を1回のディスク書き込みにまとめる」ことができ、I/O回数を大幅に削減できます。ただし、ダーティページがまだディスクに反映されていない状態でサーバーがクラッシュするとデータが失われる可能性があるため、これを防ぐために**WAL/トランザクションログ**という仕組みが必須になります(次章以降で詳しく扱います)。

---

## まとめ

- バッファプールは、ディスクI/Oを削減するためのメモリキャッシュであり、DB性能の要。
- 単純なLRUではなく、一括スキャンによるキャッシュ汚染を防ぐ工夫(young/oldサブリストなど)が各製品に実装されている。
- PostgreSQLはOSキャッシュとの併用を前提、MySQL/SQL ServerはDBプロセス自身で完結させる思想が強い、という違いがある。
- 次章([05_トランザクションと同時実行制御](./05_トランザクションと同時実行制御.md))では、この「メモリ上の同じデータに複数の接続が同時にアクセスするとき、何が起きるか」を扱います。
