## この章のゴール

DBサーバーを「1つの大きなブラックボックス」ではなく、役割ごとの部品の集まりとして捉えられるようになることがゴールです。以降の章(ストレージ、インデックス、トランザクションなど)は、すべてこの章で説明する部品のどれかに対応しています。

---

## クライアントサーバーモデル

RDBMSは基本的に**クライアントサーバーモデル**で動作します。

```
[アプリケーション]  --- SQL文を送る --->  [DBサーバー]
[アプリケーション]  <--- 結果を返す ---  [DBサーバー]
```

- アプリケーション(クライアント)は直接ファイルを読み書きしません。必ずDBサーバーに「このSQLを実行してほしい」とリクエストを送り、DBサーバーがディスク上のファイルを操作して結果を返します。
- これにより、複数のアプリケーションが同時に同じデータへアクセスしても、DBサーバーが交通整理を行い、データの整合性を保てます(この交通整理の仕組みが [05章](./05_トランザクションと同時実行制御.md) のテーマです)。

## 接続を受け取ってから結果を返すまでの流れ

たとえば `SELECT * FROM users WHERE id = 1;` を実行すると、DBサーバー内部ではおおよそ次の順で処理が進みます。

1. **接続受付**: クライアントとのTCP接続を確立する(認証も含む)。
2. **構文解析(パース)**: SQL文が文法的に正しいか確認し、内部データ構造(構文木)に変換する。
3. **意味解析**: テーブルやカラムが実在するか、権限があるかを確認する。
4. **最適化(オプティマイザ)**: どのインデックスを使うか、どういう順序でテーブルを結合するかなど、複数の実行方法の中から最も速そうな「実行計画」を選ぶ。
5. **実行(エグゼキュータ)**: 実行計画に従って、実際にインデックスやテーブルのデータを読みに行く。
6. **バッファプール参照**: データはまずメモリ上のキャッシュ(バッファプール)にあるか確認し、なければディスクから読み込んでキャッシュに載せる。
7. **結果返却**: 取得した行をクライアントに返す。

更新系(`INSERT`/`UPDATE`/`DELETE`)の場合は、5〜6の間に**ログ(WAL/トランザクションログ)への書き込み**と**ロック取得**が挟まります。この一連の流れの3〜5番は [07章](./07_クエリ処理とオプティマイザ.md)、6番は [04章](./04_バッファプールとキャッシュ.md)、更新系の詳細は [05章](./05_トランザクションと同時実行制御.md) と [06章](./06_ログと障害復旧.md) で扱います。

## プロセスモデル vs スレッドモデル

クライアントからの接続を、DBサーバーが内部でどう捌くかには大きく2つの方式があります。

### マルチプロセスモデル(PostgreSQL)

PostgreSQLは、クライアントが接続してくるたびに**OSのプロセス**を1つ新しく生成し、そのプロセス(バックエンドプロセス)が接続の生存期間中ずっとそのクライアントを専属で担当します。全体を統括する親プロセスは「postmaster」と呼ばれます。

> PostgreSQLは「postmaster」と呼ばれる親プロセスが接続を受け付け、接続ごとに専用の「バックエンドプロセス」を生成してクライアントを1対1で担当させるマルチプロセスアーキテクチャを採用しています。バックエンドプロセスは単一スレッドで動作し、一度に1つのクエリしか実行できません。(出典: [PostgreSQL公式ドキュメント: Overview of PostgreSQL Internals](https://www.postgresql.org/docs/current/overview.html), [The Internals of PostgreSQL - Process Architecture](https://www.interdb.jp/pg/pgsql02/01.html))

- プロセスはOSレベルで完全に分離されているため、1接続がクラッシュしても他の接続に影響しにくいという利点があります。
- 一方で、接続数が増えるとプロセス生成・切り替えのコストが無視できなくなるため、実運用では **PgBouncer** などのコネクションプーラーを間に挟むのが定石です。

### マルチスレッドモデル(MySQL / SQL Server)

MySQLとSQL Serverは、接続ごとに軽量な**スレッド**を割り当てるマルチスレッドアーキテクチャを採用しています。

- スレッドはプロセスよりも生成・切り替えのコストが低いため、大量接続をさばきやすい設計です。
- 反面、同一プロセス内のメモリ空間を共有するため、バグの影響範囲がプロセス全体に及びやすいという側面もあります。

## 論理層としてのアーキテクチャ(MySQLの3層構造)

MySQLはさらに、**SQLを解釈する層**と**実際にデータを保存する層**が明確に分離した設計になっている点が特徴です。

> MySQLのアーキテクチャは大きく分けて、クライアントとの接続を扱う「コネクタ層」、SQLパーサ・オプティマイザ・キャッシュなどを持つ「SQL層(サーバー層)」、そして実データの読み書きを担当する「ストレージエンジン層」の3層で構成されます。ストレージエンジン層は差し替え可能な「プラガブルストレージエンジンアーキテクチャ」になっており、InnoDB・MyISAM・Archiveなど用途に応じたエンジンを選択できます。(出典: [MySQL公式ドキュメント: Overview of MySQL Storage Engine Architecture](https://dev.mysql.com/doc/refman/8.0/en/pluggable-storage-overview.html), [MySQL公式ドキュメント: The Common Database Server Layer](https://dev.mysql.com/doc/refman/8.0/en/pluggable-storage-common-layer.html))

PostgreSQLとSQL Serverには、この「ストレージエンジンの差し替え」という概念は基本的にありません(SQL層とストレージ層が一体化しています)。これはMySQL特有の設計思想です。

---

## 製品ごとのアーキテクチャの違い

| 観点 | PostgreSQL | MySQL(InnoDB) | SQL Server |
|---|---|---|---|
| 接続の処理単位 | プロセス(マルチプロセス) | スレッド(マルチスレッド) | スレッド(マルチスレッド、SQLOSが独自スケジューリング) |
| ストレージエンジン | 単一(内蔵) | 差し替え可能(プラガブル、標準はInnoDB) | 単一(内蔵) |
| 大量接続時の定石 | コネクションプーラー(PgBouncer等)を挟む | スレッドプールで比較的スケールしやすい | スレッドプール機構を内蔵 |
| 拡張性の考え方 | 拡張機能(Extension)やプラグイン機構が豊富 | ストレージエンジンごとプラグイン化 | Microsoft製品群との統合(SSIS/SSRS等)が強み |

## まとめ

- DBサーバーは「クライアントからSQLを受け取り→解析→最適化→実行→結果を返す」というパイプラインを持つ。
- PostgreSQLは**プロセス単位**、MySQL/SQL Serverは**スレッド単位**で接続を処理する、という設計思想の違いが根本にある。
- MySQLは「SQLを解釈する層」と「データを保存する層(ストレージエンジン)」が分離しており、差し替え可能。PostgreSQL/SQL Serverは一体型。
- 次章([02_ストレージとページ構造](./02_ストレージとページ構造.md))では、この図の一番下の層である「ディスク上の物理的なデータの並び方」を見ていきます。
