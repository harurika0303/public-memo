## この章のゴール

ここまでの章で、ストレージ・インデックス・キャッシュ・トランザクション・ログという「土台」を見てきました。この最終章では、その土台の上でSQL文が実際にどう処理されるか、特に「なぜこのインデックスが使われて、あのインデックスは使われないのか」を決める**オプティマイザ**の考え方を扱います。

## SQLが実行されるまでの4段階

[01章](./01_全体アーキテクチャ.md)でも触れましたが、あらためて詳しく見ていきます。

```
SQL文(テキスト)
   │
   ▼
① パーサ(構文解析)  … 文法エラーがないか確認し、構文木に変換
   │
   ▼
② リライト/意味解析   … ビューの展開、権限チェック、テーブル/カラムの実在確認
   │
   ▼
③ オプティマイザ(プランナ) … 複数の「実行方法の候補」を作り、最もコストが低そうなものを選ぶ
   │
   ▼
④ エグゼキュータ      … 選ばれた実行計画に従って、実際にインデックスやテーブルを読みに行く
   │
   ▼
結果セット
```

①〜②は「SQLとして正しいか」を確認する段階、③〜④が「どう速く実行するか」を決めて実行する段階です。この③が今回の主役です。

## オプティマイザは何をしているのか

同じ結果を返すSQLでも、実行方法(実行計画)は複数考えられます。例えば `WHERE` 句にインデックスがある場合、次のような選択肢があります。

- インデックスを使って絞り込む(Index Scan)
- インデックスを使わずテーブル全体を読む(Seq Scan / Table Scan)
- インデックスだけで完結させる([03章](./03_インデックス構造.md)のIndex-Only Scan)

複数テーブルのJOINがあれば、「どの順番で結合するか」「Nested Loop / Hash Join / Merge Joinのどれを使うか」といった選択肢も加わります。オプティマイザの仕事は、**これらの組み合わせの中から「最もコストが低そう」なものを1つ選ぶ**ことです。

> SQL Serverのクエリオプティマイザは、テーブルやインデックスから情報を抽出するための異なる方式のリソースコストを見積もる際に、分布統計情報を利用します。オプティマイザは入力としてクエリ・データベーススキーマ・データベース統計情報を受け取り、出力としてクエリ実行プランを生成します。重要なのは、オプティマイザは単に最もリソースコストが低いプランを選ぶのではなく、妥当なリソースコストで最も速く結果を返すプランを選ぶという点です。例えば並列実行はシリアル実行よりも多くのリソースを消費しますが、より速く完了するため、サーバー全体の負荷に悪影響がなければオプティマイザは並列実行プランを選択します。(出典: [Microsoft Learn: Query Processing Architecture Guide](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17))

## 統計情報とコスト見積もり

オプティマイザが「このインデックスを使えば何行くらいヒットしそうか」を見積もるために使う材料が**統計情報**です。テーブルの行数、カラムの値の分布(ヒストグラム)、重複度合いなどが記録されています。

> MySQLのオプティマイザは、クエリ実行中に発生するさまざまな操作のコストの見積もりに基づいた「コストモデル」を使用します。列の値に関するヒストグラム統計は `column_statistics` データディクショナリテーブルに保持され、`INFORMATION_SCHEMA.COLUMN_STATISTICS` で参照できます。ヒストグラムの管理は `ANALYZE TABLE` 文を通じて行います。(出典: [MySQL公式ドキュメント: 10.9.5 The Optimizer Cost Model](https://dev.mysql.com/doc/refman/8.0/en/cost-model.html))

統計情報が古い(実データとかけ離れている)と、オプティマイザの見積もりが外れ、非効率な実行計画が選ばれてしまいます。「統計情報の更新」は、DBのパフォーマンス不調時に確認すべき定番のチェックポイントです(この点は同フォルダ内の [A5M2_実行計画の読み方.md](./../A5M2_実行計画の読み方.md) でも扱っています)。

> SQL Serverは、クエリが何行を返すかを見積もるために統計情報に依存しており、統計情報が古くなっていると、カーディナリティ(行数)の見積もりが不正確になり、オプティマイザが非効率な実行プランを選んでしまう原因になります。(出典: [Microsoft Learn: Query Processing Architecture Guide](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17))

## 結合順序の探索問題とその対処

テーブルの結合(JOIN)数が増えると、「どの順番で結合するか」の組み合わせ数は指数関数的に爆発します(5テーブルのJOINで100通り以上、10テーブルでは天文学的な数になります)。すべての組み合わせを厳密に評価していると、オプティマイザ自体の実行時間が無視できなくなります。

PostgreSQLはこの問題に対して、テーブル数が一定以上になると**遺伝的アルゴリズム**に切り替えるというユニークな工夫をしています。

> GEQO(Genetic Query Optimizer、遺伝的問い合わせ最適化)は、ヒューリスティックな探索を用いてクエリプランニングを行うアルゴリズムです。多数のリレーションを結合する複雑なクエリに対して、プランニング時間を削減しますが、その代償として通常の網羅的探索アルゴリズムで見つかるプランより劣ったプランになることがあります。既定では、FROM句に含まれるテーブル数が12以上(`geqo_threshold`)のクエリに対してこの遺伝的最適化が使用されます。それより単純なクエリでは、通常の網羅的探索プランナを使うのが最善です。(出典: [PostgreSQL公式ドキュメント: 61.3 Genetic Query Optimization (GEQO) in PostgreSQL](https://www.postgresql.org/docs/current/geqo-pg-intro.html))

MySQL・SQL Serverも同様に、内部的にJOIN順序の探索を打ち切るしきい値やヒューリスティックを持っています(製品ごとの詳細な実装は非公開部分も多いですが、「すべての組み合わせを毎回厳密探索しているわけではない」という考え方は共通です)。

## 製品ごとのオプティマイザの違い

| 観点 | PostgreSQL | MySQL(InnoDB) | SQL Server |
|---|---|---|---|
| 最適化方式 | コストベース(統計情報+コスト式) | コストベース(コストモデル+ヒストグラム) | コストベース(統計情報+並列実行も考慮) |
| 多数JOIN時の対処 | 遺伝的アルゴリズム(GEQO)へ切り替え | 内部的な探索の枝刈り | 内部的な探索の枝刈り、ヒント句で制御可 |
| 実行計画の確認コマンド | `EXPLAIN` / `EXPLAIN ANALYZE` | `EXPLAIN` / `EXPLAIN ANALYZE`(8.0.18以降) | 実行プランの表示(GUI/`SET SHOWPLAN_XML ON`等) |
| フルスキャンの表記 | `Seq Scan` | `ALL`(`type`列) | `Table Scan` / `Clustered Index Scan` |

## まとめ

- SQLは「パース→意味解析→最適化→実行」という順で処理される。オプティマイザは統計情報をもとに複数の実行方法の中から最も効率的と思われるものを選ぶ。
- 統計情報が古いと、正しい実行計画が選ばれなくなる。定期的な統計情報の更新は運用上重要。
- JOIN数が多いクエリでは、厳密な最適化を諦めてヒューリスティックに切り替える工夫が各製品にある(PostgreSQLのGEQOはその代表例)。
- ここまでの7章で、ディスク上の物理構造からSQLの実行計画まで、DB内部構造の全体像を一通り学びました。製品ごとの違いを一覧で振り返りたい場合は [08_製品比較まとめ.md](./08_製品比較まとめ.md) を参照してください。
