# DataSpiderのトランザクション設定と現在の構成での挙動の考察

## 1. DataSpiderのトランザクション設定の仕組み

### 1.1 基本方式(JTA準拠)

<cite index="22-1">DataSpider Servistaのトランザクション管理はJ2EEの標準的な枠組みである「JTA(Java Transaction API)」に準拠しています。</cite><cite index="21-1">DataSpiderでは「スクリプト単位」と「指定した処理単位」でトランザクションを設定することができます。</cite>

| 設定単位 | 概要 |
|---|---|
| スクリプト単位 | スクリプト(フロー)全体に対して、6種類のトランザクション属性のいずれかを設定する方式 |
| 指定した処理単位 | フロー内の一部区間だけを[トランザクション]コンポーネントで囲んで制御する方式 |

### 1.2 スクリプト単位のトランザクション属性(6種類)

<cite index="21-1">「スクリプト単位」でトランザクションを設定する場合、6種類のトランザクション属性を選択することができます。トランザクション属性は「呼び出し元のトランザクションの制限」という観点で設定します。</cite>

これはJTA/EJBの標準的なトランザクション属性(呼び出し元のトランザクションに参加するか、新規に開始するか、トランザクションなしで実行するか等)に準じたもので、代表的なものとして以下のような種類があります。

| 属性 | 動作の考え方 |
|---|---|
| Required | 呼び出し元のトランザクションがあればそれに参加し、なければ新規に開始する |
| RequiresNew | 呼び出し元のトランザクションの有無に関わらず、常に新規トランザクションを開始する |
| **Supports** | 呼び出し元のトランザクションがあればそれに参加し、**なければトランザクションを開始せずに実行する** |
| NotSupported | 呼び出し元のトランザクションがあっても参加せず、常にトランザクションなしで実行する |
| Mandatory | 呼び出し元のトランザクションが必須。なければエラーとなる |
| Never | 呼び出し元のトランザクションがあってはならない。あればエラーとなる |

### 1.3 [トランザクション]コンポーネント(指定した処理単位)

<cite index="21-1">指定した処理単位でトランザクションを設定する場合には、トランザクションコンポーネントを使用します。トランザクションコンポーネントは常に新規のトランザクションを開始します。トランザクション属性のREQUIRES_NEWと同様の動作となります。</cite>

つまり、[トランザクション]コンポーネントで囲んだ区間は、スクリプト単位の設定に関係なく強制的に1つの新規トランザクションとしてまとめられます。**今回の環境ではこのコンポーネントを使用していない**ため、DELETE処理・INSERT処理を強制的に1つのトランザクションとしてまとめる仕組みは働いていません。

### 1.4 トランザクション対応アダプタのデフォルト挙動

<cite index="21-1">トランザクションをサポートしているアダプタは通常、コンポーネントアイコン単位でトランザクション処理を行います。スクリプトのトランザクション属性やトランザクションコンポーネント内に配置された場合などは、そのトランザクションに参加します。</cite>

これが今回のケースで最も重要なポイントです。**[トランザクション]コンポーネントで囲っておらず、かつ呼び出し元のトランザクションが存在しない状態では、各DBアダプタのコンポーネントは「コンポーネントアイコン単位」で独立してトランザクション処理(=コミット)を行う**という挙動になります。

### 1.5 補足: グローバルリソースの自動コミット設定

DB接続設定(グローバルリソースのプロパティ)には「自動コミットを行う」という項目があり、これが有効になっているとDataSpiderのトランザクション制御に関わらずSQL文単位で自動コミットされる、という報告例もあります。この設定がDataSpider側のトランザクション属性の挙動と干渉するケースがあるため、実際の設定値をあわせて確認しておくことを推奨します。

## 2. あなたの環境(トランザクション属性: Supports、トランザクションコンポーネント未使用)での状態

### 2.1 整理

- [トランザクション]コンポーネントで囲っていない → 「指定した処理単位」での強制的なトランザクションのまとめは発生しない
- スクリプト単位のトランザクション属性が **Supports**(デフォルト)
- このスクリプトはおそらくバッチジョブとして直接起動されており、**呼び出し元のトランザクションは存在しない**

Supportsは「呼び出し元のトランザクションがあれば参加し、なければトランザクションを開始せずに実行する」という属性です。呼び出し元のトランザクションが存在しない今回のようなケースでは、**スクリプト全体を包む上位トランザクションは存在しない状態**になります。

### 2.2 各コンポーネントの挙動

上位トランザクションが存在しないため、1.4で述べた「コンポーネントアイコン単位でのトランザクション処理」が適用されます。つまり、

- DELETE処理を行うコンポーネント → そのコンポーネント単体で1つのトランザクションとして実行・完了時にコミット
- SELECT(ビュー)→INSERTを行うコンポーネント → そのコンポーネント単体で1つのトランザクションとして実行・完了時にコミット

という形で、**コンポーネントごとに独立してコミットされる**という認識は、DataSpiderの仕様上おおむね妥当です。

### 2.3 「削除中・挿入中以外は正常」という見解についての考察

この見解は構造としては妥当ですが、いくつか前提を確認しておく必要があります。**前提が崩れると、想定より長い時間・広い範囲でSELECTがブロックされる可能性があります。**

#### 確認すべき前提①: DELETEとINSERTは本当に別コンポーネントか

「コンポーネントアイコン単位」でのコミットという仕様上、**1つのコンポーネントの中で複数のSQL文(例: DELETE文とINSERT文)を1回のアダプタ呼び出しでまとめて実行している場合**、その2つのSQL文は同一コンポーネント=同一トランザクションとして扱われ、削除中と挿入中の間も含めて連続してロックが保持される可能性があります。

- [ ] DELETEとINSERTがキャンバス上で別々のアイコン(コンポーネント)になっているか確認する
- [ ] 1つのDBアダプタ内で複数のSQL文をまとめて実行する設定になっていないか確認する

#### 確認すべき前提②: INSERTコンポーネント自体の処理方式

「ビューから取得したデータをINSERTする」処理が、DB側で完結する `INSERT INTO テーブル SELECT * FROM ビュー` のような**単一のSQL文**なのか、それとも**DataSpider側でビューの検索結果を一旦取得し、1行ずつINSERT文をループ実行する**方式なのかによって、ロックの保持のされ方が変わります。

| 実装方式 | ロックの保持され方 |
|---|---|
| 単一の `INSERT ... SELECT` 文 | ビューの読み取りからINSERT完了までがDB内の1つの暗黙トランザクションとなり、ビューが遅ければその分だけロック保持時間が長くなる |
| DataSpider側でSELECT結果を取得後、ループでINSERT | ループ全体が1コンポーネントの処理としてまとまっている場合、ループが完了してコミットされるまでロックが保持される可能性がある(自動コミット設定やループ内のコミット制御次第) |

いずれの場合も、**「挿入処理中」の時間の長さ自体が、ビューのパフォーマンスにほぼ比例して長くなる**という点に注意が必要です。つまり、ビューが遅いことと、SELECTがブロックされる時間が長いことは、「原因が別」というより「削除中・挿入中という限られた区間の中に、ビューの遅さがそのまま反映されている」という関係になっている可能性があります。

#### 確認すべき前提③: 自動コミット設定との整合性

1.5で触れた「自動コミットを行う」設定によっては、コンポーネント単位のコミットという想定と実際の挙動がずれる可能性があります。

- [ ] 対象DBアダプタのグローバルリソースで「自動コミットを行う」が有効か無効か確認する
- [ ] 有効な場合、SQL文単位で自動コミットされるため、想定よりも短い単位でロックが解放されている可能性がある(むしろブロッキング時間の観測結果と矛盾がないか確認材料になる)

#### 確認すべき前提④: 実際の観測との突き合わせ

ここまでは設定・仕様からの理論上の推測です。最終的には、以前まとめた `sys.dm_tran_locks` 等によるロック監視クエリを、**DataSpiderの各コンポーネントの実行タイミングと突き合わせながら**実行し、

- ブロッキングが発生している時間帯が、本当にDELETE実行中・INSERT実行中の区間と一致しているか
- それ以外の区間(例: フロー内の他の処理中)でブロッキングが発生していないか

を実測で確認することが、見解を裏付ける最も確実な方法です。

## 3. まとめ

| 項目 | 内容 |
|---|---|
| 現在の設定 | [トランザクション]コンポーネント未使用、スクリプト属性はSupports(デフォルト) |
| 結果として起きること | 呼び出し元トランザクションが存在しないため、各DBアダプタコンポーネントは独立してコミットされる(コンポーネントアイコン単位) |
| あなたの見解 | 「削除中・挿入中以外は正常」という理解は、仕様上は妥当な推測 |
| ただし要確認 | ①DELETE/INSERTが本当に別コンポーネントか、②INSERT処理が単一SQLかループ処理か、③自動コミット設定との整合性、④実際のロック監視による裏付け |
| 補足 | 挿入処理中の時間自体がビューの遅さにほぼ比例するため、「ビューが遅い」ことと「SELECTがブロックされる時間が長い」ことは矛盾せず、同じ区間の中で説明がつく可能性が高い |
