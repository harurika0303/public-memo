# DataSpider処理中にSELECTができなくなる現象の切り分け手順

## 現象の整理

> テーブルのデータをDELETEし、ビューから取得したデータをINSERTする処理を実行している。
> - 処理に時間がかかっている
> - その処理が動いている間、他のセッションからSELECTができなくなる

この2つの症状は**原因が同じとは限らない、切り分けが必要な別問題**です。

| 症状 | 疑われる原因の切り口 |
|---|---|
| ① 処理そのものが遅い | ビュー(SELECT元)のパフォーマンス問題 |
| ② 処理中に他からSELECTできない | ロック・トランザクションの問題(排他ロックの保持時間・範囲) |

**重要なポイント**: たとえビュー自体は速くても、DELETE→INSERTを1つの巨大なトランザクションで実行していれば、処理時間 = ロック保持時間となり、他のSELECTがブロックされます。逆にビューが遅ければ、その分INSERT元データの取得に時間がかかり、結果的にトランザクションが長引いて同じくSELECTがブロックされます。**この2つが絡み合っている可能性が高いため、まず両者を切り離して確認することが重要です。**

---

## 切り分けの全体方針

```
1. ビュー単体の性能を、DataSpiderを介さずに直接確認する
        ↓
2. DataSpiderのトランザクション・コミット設定を確認する
        ↓
3. 処理実行中に実際のロック状況をDB側で観測する
        ↓
4. DELETE/INSERTの実装方式(一括か分割か)を確認する
        ↓
5. DBの分離レベル・ロックエスカレーションの設定を確認する
```

---

## 手順1: ビュー単体のパフォーマンスを確認する

DataSpiderを経由せず、DBクライアントツール(SSMS・A5M2など)から直接ビューのSELECTを実行し、**単体で時間がかかっているかどうか**を切り分けます。

### 確認すること

- [ ] ビューへの `SELECT * FROM ビュー名` を単体実行し、実行時間を計測する
- [ ] 実行計画を取得し、フルスキャンやコストの高いオペレーションがないか確認する(参考: [SQL Serverの実行計画確認方法](#) / A5M2の場合は赤字表示箇所に注目)
- [ ] ビューの定義を確認し、以下がないかチェックする
  - 複数テーブルの結合(特に大量データ同士の結合)
  - ビューの中でさらに別のビューを参照している(ネストしたビュー)
  - 相関サブクエリ・スカラー関数呼び出し
  - `ORDER BY` や `DISTINCT` などソートを伴う処理
- [ ] ビューを構成する元テーブルに以下がないか確認する
  - 結合キー・絞り込み条件に対する適切なインデックスの有無
  - 統計情報が古くなっていないか(直近に大量データが更新されていないか)
  - 行数に対して想定より処理が遅い場合、統計情報の更新を試す

### SQL Serverの場合の統計情報更新例

```sql
UPDATE STATISTICS [対象テーブル名];
-- またはデータベース全体
EXEC sp_updatestats;
```

### 判断基準

| 結果 | 判断 |
|---|---|
| 単体実行でも遅い | ビュー自体のパフォーマンス問題である可能性が高い → チューニングが必要 |
| 単体実行では速い | DataSpider経由の処理・トランザクションの持ち方に問題がある可能性が高い |

## 手順2: DataSpiderのトランザクション・コミット設定を確認する

DataSpiderでは、フロー全体または[トランザクション]コンポーネントで囲んだ範囲を1つのトランザクションとして扱うことができます。DELETE〜INSERTが同一トランザクション内で実行されている場合、**処理全体が完了(コミット)するまでロックが保持され続ける**ため、他セッションのSELECTがブロックされる直接的な原因になります。

### 確認すること

- [ ] フロー内でDELETE処理とINSERT処理が[トランザクション]コンポーネントで囲まれていないか確認する
- [ ] 囲まれている場合、そのトランザクションの範囲(スクリプト単位か、指定した単位か)を確認する
- [ ] 対象DBアダプタの接続設定(グローバルリソースのプロパティ)で「自動コミットを行う」設定が有効になっているか確認する
  - 有効(自動コミット)の場合、SQL文単位でコミットされるため、ロック保持時間は短くなる傾向
  - 無効(明示的トランザクション)の場合、コミットするまで全体がロックされ続ける
- [ ] INSERTが1件(または1バッチ)ごとにコミットされる設計か、全件処理後に一括コミットする設計かを確認する
- [ ] DELETE対象の行数、INSERT対象の行数のボリュームを把握する(件数が多いほどロック保持時間・範囲が拡大しやすい)

### 判断基準

| 設定 | 影響 |
|---|---|
| DELETE〜INSERT全体を1トランザクションで実行 | 処理完了までロックが保持され、SELECTがブロックされ続ける典型パターン |
| バッチ単位・件数単位でコミットを分割 | ロック保持時間が短くなり、ブロッキングも短時間で解放される |

## 手順3: 処理実行中に実際のロック状況を観測する

DataSpiderの処理を実際に動かしながら、DB側からロックの状況をリアルタイムで確認します。これにより「何のロックが」「どのテーブルに対して」「どのくらいの時間」保持されているかを直接特定できます。

### SQL Serverの場合

```sql
SELECT 
    tl.request_session_id,
    OBJECT_NAME(p.object_id) AS table_name,
    tl.resource_type,
    tl.request_mode,
    tl.request_status,
    er.wait_type,
    er.wait_time,
    er.status AS query_status,
    st.text AS sql_text
FROM sys.dm_tran_locks tl
LEFT JOIN sys.partitions p 
    ON tl.resource_associated_entity_id = p.hobt_id
LEFT JOIN sys.dm_exec_requests er 
    ON tl.request_session_id = er.session_id
OUTER APPLY sys.dm_exec_sql_text(er.sql_handle) st
WHERE tl.resource_type = 'OBJECT'
ORDER BY tl.request_session_id;
```

### 確認すること

- [ ] DataSpiderのセッションが保持している `request_mode`(ロックモード)を確認する
  - `X`(排他ロック)がテーブル全体(`OBJECT`単位)に対して長時間かかっている場合、テーブルロックが原因でSELECTがブロックされていると判断できる
  - `IX`(意図排他)であれば行/ページ単位のロックであり、他のSELECTは通常ブロックされにくいはずだが、分離レベルによってはブロックされる
- [ ] SELECTしようとしているセッションの `wait_type` が `LCK_M_S` などロック待ちを示しているか確認する
- [ ] ブロッキングの原因セッション(`blocking_session_id`)がDataSpiderの接続と一致しているか確認する
- [ ] 処理の進行に伴い、ロック対象が徐々に拡大していないか(=ロックエスカレーションの兆候)を確認する

### 判断基準

| 観測結果 | 判断 |
|---|---|
| テーブル全体にX(排他)ロックがかかっている | DELETE/INSERTがテーブルロックを取得している。ロックエスカレーションまたは明示的なテーブルロックが疑われる |
| 特定行・ページのみロックされているのにSELECTがブロックされる | 分離レベルの問題(READ COMMITTEDでの読み取りブロック)の可能性 |
| ロックの範囲が処理中に段階的に広がっていく | ロックエスカレーション発生の可能性が高い |

## 手順4: DELETE/INSERTの実装方式を確認する

同じ「DELETEしてINSERTする」処理でも、実装方式によってロックの影響範囲が大きく異なります。

### 確認すること

- [ ] DELETEは `DELETE FROM テーブル` のような一括削除か、それとも大量データを1行ずつ削除しているか
- [ ] INSERTはビューの結果を1行ずつINSERTしているか、まとめてバルクINSERTしているか
- [ ] DataSpiderのDBアダプタの設定で、バッチサイズ・コミット単位のプロパティが指定されているか確認する
- [ ] (SQL Serverの場合)DELETE対象が概ね5,000行を超えるようなケースでは、行ロックがテーブルロックへ自動的にエスカレーションされる可能性がある

### ロックエスカレーションの確認(SQL Server)

拡張イベントで実際にエスカレーションが発生しているか確認できます。

```sql
CREATE EVENT SESSION [LockEscalationCheck] ON SERVER
ADD EVENT sqlserver.lock_escalation(
    ACTION(sqlserver.sql_text, sqlserver.session_id)
)
ADD TARGET package0.event_file(
    SET filename = N'C:\Temp\LockEscalation.xel'
);

ALTER EVENT SESSION [LockEscalationCheck] ON SERVER STATE = START;
```

処理実行後、このイベントが記録されていれば、DELETE/INSERTのどこかでテーブルロックへのエスカレーションが発生していることが確定します。

### 判断基準

| 実装方式 | 影響 |
|---|---|
| 全件を1回のDELETE文・INSERT文で処理 | 対象行数が多いとロックエスカレーションが起きやすく、テーブル全体がロックされる可能性 |
| バッチ分割(例: 1,000件ずつコミット) | ロック保持時間・範囲が小さくなり、ブロッキングの影響が緩和される |

## 手順5: 分離レベル・DB設定を確認する

SELECT側がブロックされるかどうかは、DBの分離レベル(トランザクション分離レベル)にも依存します。

### 確認すること

- [ ] SELECTを実行している側のセッション/アプリケーションの分離レベルを確認する(既定は多くの場合 `READ COMMITTED`)
- [ ] `READ_COMMITTED_SNAPSHOT` オプションがデータベースで有効になっているか確認する(SQL Serverの場合)

```sql
SELECT name, is_read_committed_snapshot_on 
FROM sys.databases 
WHERE name = 'DB名';
```

- [ ] 有効になっていない場合、これを有効化することで、書き込み中でも読み取りがブロックされないようになる(行バージョニングを使用するため)

```sql
ALTER DATABASE 対象データベース名 SET READ_COMMITTED_SNAPSHOT ON;
```

> ⚠️ **注意**: 本設定の変更はアプリケーション全体の挙動(tempdb使用量の増加、書き込み時の競合検知の仕組みの変化など)に影響するため、事前に検証環境で確認のうえ適用してください。

## 想定される原因パターンと対処の方向性

| パターン | 症状の特徴 | 対処の方向性 |
|---|---|---|
| ビュー自体が遅い | DataSpiderを介さない単体SELECTでも時間がかかる | ビューのインデックス見直し、統計情報更新、ビュー定義の最適化 |
| DELETE〜INSERTが1トランザクションで長時間実行 | ビュー単体は速いが、DataSpider実行中は長時間ロックが継続する | コミット単位を分割する、DataSpiderのトランザクション設定を見直す |
| ロックエスカレーションでテーブルロック化 | 処理途中からロック範囲が段階的に拡大する | バッチサイズを小さくする、DELETE/INSERTを分割実行する |
| 分離レベルの影響でSELECTがブロックされる | 行ロックなのにSELECTがブロックされる | `READ_COMMITTED_SNAPSHOT` の有効化を検討する |
| DELETE+INSERTの設計自体に起因 | テーブルを全件入れ替える設計そのものが長時間ロックを招く | ステージングテーブルへ先にINSERTしてからテーブル入れ替え(スキーマ変更/パーティションスイッチ等)方式へ設計変更を検討 |

---

## 補足: 根本的な設計改善案(参考)

原因切り分けの結果、DELETE→INSERTという「全件入れ替え」の設計自体が長時間ロックの根本原因であると判明した場合、以下のような設計変更が有効なことがあります。

- **ステージングテーブル方式**: 別のワークテーブルに先にINSERTしてから、完了後に本番テーブルと入れ替える(テーブル名変更やパーティションスイッチを利用)ことで、本番テーブルへのロック時間を最小化する
- **差分更新方式**: 全件DELETE→INSERTではなく、変更があった行のみをUPDATE/INSERT/DELETEする差分方式に変更し、処理対象行数自体を減らす
- **バッチコミット方式**: DataSpiderのループ処理で一定件数ごとにコミットを行い、1回のトランザクションで保持するロック量を抑える

## チェックリストまとめ

- [ ] ビュー単体のSELECT実行時間を計測した
- [ ] ビューの実行計画を確認し、フルスキャン等の問題箇所を特定した
- [ ] DataSpiderのトランザクション設定(コミット単位・自動コミット有無)を確認した
- [ ] DataSpider実行中に `sys.dm_tran_locks` 等でロック状況を観測した
- [ ] DELETE/INSERTが一括処理かバッチ処理か確認した
- [ ] ロックエスカレーションの発生有無を確認した
- [ ] SELECT側の分離レベル・`READ_COMMITTED_SNAPSHOT` 設定を確認した
