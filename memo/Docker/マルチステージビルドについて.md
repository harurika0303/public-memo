## マルチステージビルドとは

1 つの Dockerfile に複数の `FROM` 命令を書くことで、**ビルド用の環境と実行用の環境を分離**する手法です。

ビルドに必要なツール（コンパイラ・SDK・テストフレームワークなど）を最終イメージに含めず、実際に動かすファイルだけを最終ステージにコピーすることで、**イメージを軽量・安全に保つ**ことができます。

### シングルステージビルドとの比較

```
シングルステージ:
┌──────────────────────────────────┐
│ golang:1.25 (800MB+)             │
│ + ソースコード                    │
│ + ビルドツール・依存関係           │
│ + バイナリ（本当に必要なもの）      │  ← すべてが最終イメージに入る
└──────────────────────────────────┘

マルチステージ:
┌──────────────────────────────────┐
│ ステージ 1: golang:1.25 (ビルド用) │
│   ソースコード、ツール → バイナリ生成 │
└──────────────┬───────────────────┘
               │ バイナリだけコピー
               ▼
┌──────────────────────────────────┐
│ ステージ 2: scratch / alpine (数MB)│
│   バイナリのみ                    │  ← 最終イメージは最小限
└──────────────────────────────────┘
```

## 基本的な書き方

### ステージの参照方法

デフォルトでは番号（0 から始まる整数）でステージを参照できますが、`AS 名前` で名前を付けることが推奨されます。

```dockerfile
# 番号で参照（非推奨：順番が変わると壊れる）
FROM golang:1.25
RUN go build -o /bin/app .

FROM scratch
COPY --from=0 /bin/app /bin/app  # ← 0 番目のステージから取得
```

```dockerfile
# 名前で参照（推奨）
FROM golang:1.25 AS build
RUN go build -o /bin/app .

FROM scratch
COPY --from=build /bin/app /bin/app  # ← build ステージから取得
```

### `COPY --from` の構文

```dockerfile
COPY --from=<ステージ名またはイメージ名> <コピー元パス> <コピー先パス>
```

`--from` には以下を指定できます：

| 指定方法     | 例                    | 説明                       |
| ------------ | --------------------- | -------------------------- |
| ステージ名   | `--from=build`        | 同 Dockerfile 内のステージ |
| ステージ番号 | `--from=0`            | 0 から始まる番号           |
| 外部イメージ | `--from=nginx:latest` | Docker Hub などのイメージ  |

## 言語・用途別の具体例

### Go アプリケーション

Go は静的リンクバイナリを生成できるため、`scratch`（空のイメージ）を最終ステージに使えます。

```dockerfile
# syntax=docker/dockerfile:1

# ステージ 1: ビルド
FROM golang:1.25 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /bin/app ./cmd/app

# ステージ 2: 実行（scratch = 何も入っていない空のイメージ）
FROM scratch
COPY --from=build /bin/app /bin/app
ENTRYPOINT ["/bin/app"]
```

**最終イメージのサイズ**: Go SDK（800MB+）→ バイナリのみ（数 MB）

> `CGO_ENABLED=0` は C ライブラリへの依存をなくして完全な静的バイナリにするための設定です。

### Node.js アプリケーション（3 ステージ構成）

```dockerfile
# syntax=docker/dockerfile:1

# ステージ 1: 依存関係インストール
FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

# ステージ 2: ビルド（TypeScript コンパイルなど）
FROM deps AS builder
COPY . .
RUN npm run build

# ステージ 3: 本番用（dev の依存関係を除く）
FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
# 本番用の依存関係だけインストール
COPY package*.json ./
RUN npm ci --only=production
# ビルド済みファイルだけコピー
COPY --from=builder /app/dist ./dist
# root 以外のユーザーで実行
USER node
CMD ["node", "dist/server.js"]
```

### Python アプリケーション

```dockerfile
# syntax=docker/dockerfile:1

# ステージ 1: 依存関係ビルド
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# ステージ 2: 実行
FROM python:3.12-slim AS runner
WORKDIR /app
# インストールされたパッケージだけコピー
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "app.py"]
```

### Java / Maven アプリケーション

```dockerfile
# syntax=docker/dockerfile:1

# ステージ 1: ビルド
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
# 依存関係だけ先にダウンロードしてキャッシュを活用
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

# ステージ 2: 実行
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

Maven（700MB+）→ JRE のみ（約 200MB）

### 共通のベースステージを再利用する

複数のターゲット間で共通の準備処理を共有できます。

```dockerfile
# syntax=docker/dockerfile:1

# 共通ベースステージ
FROM alpine:latest AS base
RUN apk --no-cache add build-base

# ターゲット A: ソース 1 をビルド
FROM base AS build-a
COPY source_a.cpp source.cpp
RUN g++ -o /binary_a source.cpp

# ターゲット B: ソース 2 をビルド（base の準備を再利用）
FROM base AS build-b
COPY source_b.cpp source.cpp
RUN g++ -o /binary_b source.cpp

# 最終イメージ: 両方のバイナリを含む
FROM alpine AS final
COPY --from=build-a /binary_a /usr/local/bin/binary_a
COPY --from=build-b /binary_b /usr/local/bin/binary_b
```

### 外部イメージからファイルをコピーする

Dockerfile 内で定義したステージ以外に、既存のイメージから直接ファイルをコピーすることもできます。

```dockerfile
FROM myapp:latest AS runner
# nginx の設定ファイルを公式イメージから取得する
COPY --from=nginx:1.27 /etc/nginx/nginx.conf /etc/nginx/nginx.conf
```

## `--target` で特定のステージまでビルドする

```bash
docker build --target <ステージ名> -t <タグ> .
```

### 使いどころ

| 用途                             | 例                                            |
| -------------------------------- | --------------------------------------------- |
| 中間ステージのデバッグ           | `--target build` でビルド後の状態を確認する   |
| テスト用イメージのビルド         | `--target test` でテストのみ実行する          |
| 開発用とプロダクション用を分ける | `--target dev` / `--target prod` を使い分ける |

```dockerfile
# syntax=docker/dockerfile:1

FROM node:22-alpine AS base
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM base AS test
COPY . .
RUN npm test   # テストを実行するステージ

FROM base AS prod
COPY . .
RUN npm run build
CMD ["node", "dist/server.js"]
```

```bash
# テストだけ実行
docker build --target test -t myapp:test .

# 本番用イメージをビルド
docker build --target prod -t myapp:prod .
```

## BuildKit による最適化

BuildKit（Docker Engine 23.0 以降でデフォルト有効）では、**実際に必要なステージだけをビルドします**。

```dockerfile
FROM ubuntu AS base
RUN echo "base"

FROM base AS stage1   # stage2 が依存しないステージ
RUN echo "stage1"

FROM base AS stage2
RUN echo "stage2"
```

```bash
# BuildKit（デフォルト）: stage1 はスキップされる
docker build --target stage2 .
# => base と stage2 だけビルドされる

# 従来のビルダー: stage1 も処理してしまう
DOCKER_BUILDKIT=0 docker build --target stage2 .
# => base, stage1, stage2 すべてビルドされる
```

## マルチステージビルド利用時のポイント

### キャッシュを最大限に活用する

変更頻度の低いものを上（先）に、変更頻度の高いものを下（後）に書くことでキャッシュが効きやすくなります。

```dockerfile
FROM node:22-alpine AS deps
WORKDIR /app
# package.json だけ先にコピー（依存関係は変更が少ない）
COPY package*.json ./
RUN npm ci   # ← package.json が変わらない限りキャッシュが使われる

FROM deps AS builder
# ソースコードは変更が多いので後にコピー
COPY . .
RUN npm run build
```

### ステージ名には役割を示す名前をつける

| 推奨する名前                     | 役割                         |
| -------------------------------- | ---------------------------- |
| `deps` / `dependencies`          | 依存関係インストール         |
| `build` / `builder`              | ビルド                       |
| `test`                           | テスト実行                   |
| `dev` / `development`            | 開発用（ホットリロードなど） |
| `prod` / `production` / `runner` | 本番実行用                   |

### 最終ステージは必ずシンプルに保つ

最終ステージに含めるのは「実際に実行に必要なファイルだけ」にします。

- ソースコード → 不要（ビルド済みファイルのみ）
- テストファイル → 不要
- ビルドツール → 不要
- 開発用パッケージ（devDependencies など）→ 不要

## まとめ

| 特徴                            | 説明                                         |
| ------------------------------- | -------------------------------------------- |
| **イメージの軽量化**            | ビルドツールを最終イメージに含めない         |
| **セキュリティの向上**          | 攻撃対象となるツールやファイルを排除できる   |
| **Dockerfile 1 ファイルで完結** | ビルド用スクリプトを別途用意する必要がない   |
| **BuildKit によるビルド最適化** | 不要なステージをスキップし、並列ビルドも可能 |
| **ステージの再利用**            | 共通の準備処理を複数のターゲットで共有できる |
